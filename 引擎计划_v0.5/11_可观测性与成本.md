# 11 可观测性与成本

> 包：`engine/obs`（路径 ID、留痕、投影、成本、简报、升级队列），`internal/api` 暴露查询接口。
> 运行状态的唯一来源是 `run_events`（见 04 号）。本章讲的东西都是从事件**投影**出来的视图，以及与外部观测系统（OTel / Prometheus / slog）的对接。

---

## 1. 层级路径 ID

### 1.1 规则

```
<图名>/<子图节点label>[#r<轮次>][#e<事件序号>]/<节点label>[#<扇出序号>][@<重试次数>]
```

| 片段 | 何时出现 | 例子 |
|---|---|---|
| `根图` | 总是第一段 | `根图` |
| 子图节点 label | 进入子图引用 / 循环 / 扇出 body | `根图/闭环迭代` |
| `#rN` | 循环的第 N 轮（从 1 开始） | `根图/闭环迭代#r2` |
| `#eN` | 循环 event 模式的第 N 次唤醒 | `根图/主脑#e14` |
| `#N` | 扇出的第 N 份（从 1 开始） | `.../执行池/执行者#3` |
| `@N` | 第 N 次重试（第一次不写） | `.../执行者#3@2` |

- label 重名时追加短 ID：`决策者~7f2a`。
- label 里的 `/ # @ ~` 转义成全角字符。
- **路径用于展示和查询，node_id 用于引用**。每条事件同时带 `path` 和 `node_id + iter`（iter 是 `{round, event, fan, attempt}` 结构），所以节点改名不影响历史查询。

```go
type Iter struct { Round, Event, Fan, Attempt int }
type Loc struct {
    NodeID string `json:"node_id"`
    Path   string `json:"path"`
    Iter   Iter   `json:"iter"`
    Parent string `json:"parent_span,omitempty"`
}
func (l Loc) Child(n *graph.Node, it Iter) Loc
```

## 2. 留痕（Trace）

### 2.1 结构

一次节点执行（含重试中的每一次）就是一个 **Span**。Span 不单独建表，而是由同一 attempt 的两条 `node.state` 事件配对得到：进入 `running` 的那条和进入终态的那条；大字段只存指针。

```go
type Span struct {
    SpanID    string            `json:"span_id"`       // ULID
    ParentID  string            `json:"parent_id"`
    RunID     string            `json:"run_id"`
    Loc       Loc               `json:"loc"`
    Kind      string            `json:"kind"`          // 节点类型
    Status    string            `json:"status"`
    Start     time.Time         `json:"start"`
    End       *time.Time        `json:"end,omitempty"`
    Waits     []Wait            `json:"waits"`         // 排队/限流/审批区间
    InRef     string            `json:"in_ref"`        // ws:// 输入信封
    OutRef    string            `json:"out_ref"`       // ws:// 输出信封
    CtxRef    string            `json:"ctx_ref,omitempty"`  // 上下文装配结果（含每段 token）
    LLMCalls  []LLMCall         `json:"llm_calls,omitempty"`
    ToolCalls []ToolCall        `json:"tool_calls,omitempty"`
    Usage     Usage             `json:"usage"`
    Error     *ErrInfo          `json:"error,omitempty"`
    Attrs     map[string]string `json:"attrs,omitempty"`
}

type LLMCall struct {
    Model, Provider        string
    Start                  time.Time
    DurMs                  int64
    InTok, OutTok, CacheTok int64
    CostCNY                float64
    ReqRef, RespRef        string // ws:// 完整请求/响应（脱敏后）
    Mode                   string // native_schema | tool_call | text_repair
    Repairs                int
}
type ToolCall struct {
    Tool, Risk, IdemKey string
    Start               time.Time
    DurMs, QueueMs      int64
    Result              string // ok | error | cached | deduped
    ArgsRef, ResultRef  string
    Decision            string // allow | ask→approved | ...
}
```

### 2.2 与 OpenTelemetry 的映射

| 本系统 | OTel |
|---|---|
| Run | 根 span `harness.run`（trace_id = run_id 派生） |
| 节点执行 Span | span `harness.node`，parent = 所在子图节点的 span |
| LLMCall | 子 span `gen_ai.chat`，属性按 OTel GenAI 语义约定：`gen_ai.system`、`gen_ai.request.model`、`gen_ai.usage.input_tokens` / `output_tokens` |
| ToolCall | 子 span `harness.tool`，属性 `tool.name`、`tool.risk`、`tool.idem_key` |
| 排队/审批等待 | span event `wait.start` / `wait.end`，带 `wait.kind` |
| Op | span event `op.applied`（在设计时没有 run 的场景中，直接作为独立 span） |

- OTel 导出**可选**：配置 `OTEL_EXPORTER_OTLP_ENDPOINT` 就启用，否则不初始化。
- 本地事件日志始终是完整记录；OTel 只是投影出去的副本，可以采样。
- 属性里不放正文内容，只放指针和数值，避免把用户数据发给外部观测系统。

## 3. 时间线投影与时间旅行

### 3.1 投影

`obs.Projector` 订阅 run 的事件流，在内存里维护：

```go
type RunView struct {
    Seq      int64                  // 已处理到的事件序号
    Status   string
    Nodes    map[string]*NodeView   // key: path
    Timeline []Bar                  // 甘特条段
    Usage    Usage
    Budget   BudgetView
    Briefs   map[string]Brief       // goal_id → 最新简报
    Escal    []Escalation
}
type Bar struct {
    Path       string
    Kind       string // run | wait | queue | fail | retry
    Start, End int64  // 相对 run 开始的毫秒
}
```

- 运行中：投影增量更新，并定期持久化到 `run_views` 表（每 2 秒或每 200 条事件），重启时就不必全量重放。
- 完成后：保存最终视图，之后查询不再需要重放。

### 3.2 时间旅行查询

`GET /runs/{id}/view?at_seq=1234` 或 `?at_ms=56000`：

1. 找到 `at` 之前最近的持久化视图快照（`run_views` 按 seq 每 N 条存一份）。
2. 从该快照重放事件到 `at`。
3. 返回 RunView。

性能目标：1 万条事件的运行，任意时刻查询 < 150ms。前端拖动播放头时，每 100ms 节流请求一次；也可以一次性拉取 `?compact=1` 的全量事件，在前端本地投影（事件 < 5MB 时推荐这样做）。

## 4. 成本计量

### 4.1 价格表

```yaml
# config/pricing.yaml   单位：人民币 / 百万 tokens；可按用户实际合同修改
models:
  openai/gpt-4.1:          { in: 14.4, out: 57.6, cache_in: 3.6 }
  openai/gpt-4.1-mini:     { in: 2.9,  out: 11.5 }
  anthropic/claude-sonnet: { in: 21.6, out: 108, cache_in: 2.2 }
  local/*:                 { in: 0, out: 0 }
tools:
  web_search:              { per_call: 0.03 }
fx_note: "价格为示例，部署时按实际填写"
```

- 价格表版本化。每条 LLMCall 记录计费时使用的 `pricing_version`，以后改价不影响历史账单。
- 未知模型按 0 计价，并在运行视图里标黄"未计价"。

### 4.2 汇总口径

| 维度 | 来源 | 接口 |
|---|---|---|
| 节点 | Span.Usage | `/runs/{id}/cost?group=node` |
| 节点类型 / 模型 | LLMCall 聚合 | `?group=model` |
| 子图 | 路径前缀聚合 | `?group=path&depth=2` |
| 轮次 | Iter.Round | `?group=round` |
| 运行 | RunView.Usage | `/runs/{id}` |
| 图（历史） | runs 汇总 | `/graphs/{id}/cost?since=` |

### 4.3 预算与告警

预算来自授权书的 `Budget`、子图引用的划拨额度，以及运行参数，三者取最小值。

```go
type BudgetAccount struct {
    Limit, Used Budget
    Parent      *BudgetAccount // 子图从父级划拨
}
func (b *BudgetAccount) Reserve(est Budget) error // 调用前预留，超出返回 ErrBudget（→ authz 转 ask）
func (b *BudgetAccount) Commit(actual Budget)     // 调用后按实际结算，释放差额
```

- 调用前**预留**：按 `max_tokens` 和输入 token 估算，避免并发调用同时冲过预算线。
- 告警阈值 50% / 80% / 100%，分别发出 `budget.warn` 事件。80% 会触发规则引擎的内置降档规则（见 07 号文档）。
- 前端顶部条显示预算进度；节点详情显示该节点花费占总花费的百分比。

## 5. 日志规范（slog）

```go
logger := slog.New(redact.Handler(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: lvl})))
log := logger.With("run_id", runID, "path", loc.Path, "node_id", loc.NodeID)
log.Info("node.finished", "status", "done", "dur_ms", 1840, "tokens", 2310)
```

| 规则 | 说明 |
|---|---|
| 格式 | 生产用 JSON，开发用 `slog.TextHandler` 并加颜色 |
| 消息 | 用事件名风格（`node.finished`），不写长句 |
| 必带字段 | `run_id`、`path`、`node_id`（运行内）；`graph_id`、`op_id`（编辑时）；`req_id`（HTTP） |
| 级别 | Debug：调度细节；Info：生命周期；Warn：重试、限流、修复；Error：失败、内部错误 |
| 禁止 | 打印提示词正文、模型输出正文、密钥；这些只写入工作区指针 |
| 脱敏 | `redact.Handler` 统一替换 key 名匹配 `(?i)(api_?key|token|secret|authorization|password)` 的值 |
| 关联 | 日志带 OTel 的 trace_id / span_id（启用 OTel 时） |

## 7. 给主脑的简报

### 7.1 生成

简报由**子图端口（role=summary）**节点产生。它的执行器不调用模型，而是用确定性模板从本层投影里取数：

```go
type Brief struct {
    GoalID        string     `json:"goal_id"`      // merge_key
    Status        string     `json:"status"`       // 心跳 | 进行中 | 完成 | 阻塞
    Round         int        `json:"round"`
    Conclusion    string     `json:"conclusion"`   // ≤80 字
    CriteriaCheck []CritOK   `json:"criteria_check"`
    NeedsDecision []Question `json:"needs_decision,omitempty"`
    Evidence      []string   `json:"evidence"`     // 指针
    Cost          CostBrief  `json:"cost"`
    Seq           int64      `json:"seq"`
}
```

- `Conclusion` 来自本层判定或验收节点输出的结构化字段，不做二次总结，因此不额外花 token。只有当用户在摘要端口上设置 `summarizer: 模型引用` 时，才调用小模型压缩。
- 硬性字数上限 300 字（序列化后计算），超出时依次截断 evidence、criteria_check、conclusion。
- 触发方式：`per_round`、`on_change`（状态或判定变化时）、`heartbeat(interval)`，可以组合。

### 7.2 投递

- 简报作为信封，从摘要端口沿连线送到主脑所在循环（event 模式）的事件入口。
- 主脑侧的上下文装配使用 `merge_key=goal_id` 滚动覆盖：同一目标只保留最新一条。这样无论运行多久，主脑上下文里的简报总量都是 `目标数 × 300 字`。
- SSE `brief.updated` 同步推给前端，「给主脑的简报」面板显示最新一条和被覆盖的条数。

## 8. 升级队列

### 8.1 结构

```go
type Escalation struct {
    ID       string   `json:"id"`
    RunID    string   `json:"run_id"`
    From     Loc      `json:"from"`
    Kind     string   `json:"kind"`      // 格式错误|单任务失败|目标歧义|标准冲突|结构性无法达成|预算不足|需审批|无进展
    Severity int      `json:"severity"`  // 1 高 2 中 3 低（按 kind 默认，可在端口路由里覆盖）
    Question string   `json:"question"`
    Options  []string `json:"options,omitempty"`
    CtxRef   string   `json:"ctx_ref"`
    MergeKey string   `json:"merge_key"` // 默认 kind + from 所在子图
    Count    int      `json:"count"`     // 合并次数
    Route    string   `json:"route"`     // handled_local | bubbled:<path> | to_user
    Status   string   `json:"status"`    // open | handling | resolved
}
```

### 8.2 路由

1. 节点调用 `rc.Escalate(kind, ...)`。
2. 在所在子图的升级端口（role=escalation）上按 `routes` 匹配：
   - 命中 `to: 本层节点`：交给本层处理，`Route = handled_local`。
   - 命中 `bubble`：交给父子图的升级端口，再次匹配。
3. 一直冒泡到根图仍未被处理时：如果根图有主脑（event 循环订阅了升级事件），就交给主脑；否则交给用户，以通知和对话消息的形式出现。
4. 合并：同一 `merge_key` 在 60 秒内重复出现时只累加 `Count`，不重复唤醒处理方。
5. 优先级：处理方的事件队列按 severity 排序，同等级的按时间先后。

升级本身是事件（`escalation.raised / merged / routed / resolved`），会进入时间线和通信面板的「升级」Tab。

## 9. 前端运行监控页需要的接口

对应原型 06 和设计规范 docs/11、14：

| 界面区域 | 接口 | 说明 |
|---|---|---|
| 运行总览顶栏 | `GET /runs/{id}` + SSE `run.*`、`budget.*` | 状态、用时、tokens/预算、执行次数、当前路径 |
| 层级运行树 | `GET /runs/{id}/view` 的 `nodes`（按 path 组织成树） | 7 种状态 |
| 甘特时间线 | `view.timeline` + SSE `node.*`、`wait.*` | 增量追加条段 |
| 时间旅行 | `GET /runs/{id}/view?at_seq=` 或 `GET /runs/{id}/events?compact=1` | 二选一，详见 §3.2 |
| 节点详情 | `GET /runs/{id}/spans?path=`；`GET /ws/{ref}`（取信封、上下文） | 输入/输出信封、上下文段、工具调用、成本 |
| 从检查点重跑 / 单节点重放 | `POST /runs/{id}/rerun {from_path}`；`POST /runs/{id}/replay_node {path}` | 见 04 号文档 |
| 通信四通道 | SSE 事件按 `kind` 前缀分流：`data.*` / `ctrl.*` / `escalation.*` / `event.*` | 前端本地过滤 |
| 简报面板 | `GET /runs/{id}/briefs` + SSE `brief.updated` | |
| 资源池 | SSE `pool.usage`（每秒 1 次） | inflight、排队数、限流 |
| 成本 | `GET /runs/{id}/cost?group=` | |
| 模型诊断 | `POST /runs/{id}/diagnose` → 返回诊断结论 + 可选补丁（走 10 号文档的提议） | |
| 审计 | `GET /audit?run_id=` | |

**SSE 高频事件的节流约定**：服务端把 `node.progress`、`pool.usage` 合并为每节点每 200ms 最多 1 条；其余事件不合并。前端在 rAF 里批量应用（见设计规范 docs/17）。

## 10. 实现顺序

1. Loc / 路径 ID 与 Span 投影（M1-17，随事件流一起做）
2. RunView 投影 + `/view` + 视图快照（M2）
3. 成本：价格表、预留和结算、汇总接口（M2 末）
4. 简报、升级队列（M2，与循环、子图端口执行器同步）
5. slog 规范与脱敏（M0 就定下来）；Prometheus 指标（M5）；OTel 导出（M5）
6. 时间旅行查询性能优化（M5）
