# 08 Op 与协同编辑

> Op 是**唯一**的修改入口。人在画布上点一下、模型提交补丁、YAML 应用、系统迁移，全部变成 Op，走同一条流水线。

---

## 1. Op 信封

```go
// engine/op/op.go
type Op struct {
    ID          string          `json:"id"`           // ULID
    Kind        Kind            `json:"kind"`
    GraphID     string          `json:"graph_id"`
    Branch      string          `json:"branch"`       // main / draft-xxx
    BaseVersion int64           `json:"base_version"` // 客户端看到的版本
    Actor       Actor           `json:"actor"`        // user / model / system / external
    MandateID   string          `json:"mandate_id,omitempty"`
    Reason      string          `json:"reason,omitempty"` // 模型必填
    Taint       bool            `json:"taint,omitempty"`  // 由外部内容引出
    Target      Target          `json:"target"`       // 主要作用对象（授权与冲突检测用）
    Payload     json.RawMessage `json:"payload"`
    GroupID     string          `json:"group_id,omitempty"` // 一次用户动作 / 一个补丁内的多条 Op
    CoalesceKey string          `json:"coalesce_key,omitempty"` // 连续拖动合并
    TS          time.Time       `json:"ts"`
}

type Target struct {
    Scope string   `json:"scope"`  // 子图路径：root / root/<loopId>
    Nodes []string `json:"nodes,omitempty"`
    Edges []string `json:"edges,omitempty"`
}
```

## 2. Op 清单

| Kind | Payload（Go） | Inverse | 校验 |
|---|---|---|---|
| `add_node` | `{Scope string; Node gen.Node}` | `remove_node{IDs:[id]}` | id 未占用；type 已注册；params 合法 |
| `remove_node` | `{IDs []string}`；应用时把被删节点与相连边**快照**进 `Removed` | `restore_nodes{Removed}` | 节点存在；非 kernel 锁 |
| `restore_nodes` | `{Removed []Snapshot}`（内部用） | `remove_node` | id 未被重用 |
| `move_nodes` | `{Moves []{ID; From,To Pos}}` | 交换 From/To | — |
| `connect` | `{Edge gen.Edge; Replaced *gen.Edge}`（非 multi 端口时服务器填 Replaced） | `disconnect{ID}` + 如有 Replaced 则 `connect{Replaced}` | V05–V07、V09 |
| `disconnect` | `{IDs []string; Removed []gen.Edge}` | `connect` 逐条 | 边存在 |
| `set_param` | `{Node, Key string; From, To json.RawMessage}` | 交换 From/To | 非锁定；符合 ParamDef |
| `promote_param` | `{Node, Key string}` | `demote_param` | promotable=true |
| `demote_param` | `{Node, Key string; Removed []gen.Edge}` | `promote_param` + `connect` | — |
| `set_label` | `{Node; From, To string}` | 交换 | 长度 ≤ 80 |
| `set_tags` | `{Node; From, To []string}` | 交换 | — |
| `group` | `{Scope; NodeIDs []string; NewID string; Label string}`；应用时记录生成的入口/出口与改接的边 `Rewire` | `ungroup{NewID; Rewire}` | ≥2 节点；同一 scope |
| `ungroup` | `{ID string; Rewire *RewireLog}` | `group` | 节点有 children |
| `set_subgraph_ref` | `{Node; From, To *gen.SubgraphRef}` | 交换 | ref 存在；无引用环 |
| `set_mandate` | `{Target string; From, To *string}` | 交换 | **actor 不能是模型**，除非 mandate 允许 `set_mandate` 且只收窄（见 07） |
| `create_branch` | `{Name, From string; AtVersion int64}` | `delete_branch` | 名称唯一 |
| `delete_branch` | `{Name}` | 不可逆（软删 30 天） | 非 main |
| `merge_branch` | `{From, Into string; Base, Ours, Theirs int64; Resolutions []Resolution}` | `revert_to{Version: 合并前}` | 冲突已全部解决 |
| `apply_patch` | `{PatchID string; Ops []Op}`（模型编排产出） | 逆序展开子 Op 的 inverse | 每条子 Op 单独授权与校验；全成或全不成 |
| `revert_to` | `{Version int64; Ops []Op（服务器计算的差分）}` | `revert_to{Version: 当前}` | 版本存在 |
| `yaml_apply` | `{Ops []Op}`（服务器把 YAML diff 成细粒度 Op） | 逆序 | 同 apply_patch |
| `migrate` | `{FromSchema, ToSchema string}` | 不可逆 | 仅 system |

规则：
- **inverse 在应用时由服务器计算并存储**（客户端送来的 From 字段只作冲突检测，不信任）。
- 复合 Op（`apply_patch`、`yaml_apply`、`group`）要么全部成功，要么全部回滚（单事务）。

```go
// engine/op/apply.go
type Applier interface {
    Apply(g *graph.Graph, op *Op) (inverse *Op, touched Touched, err error)
}
type Touched struct { Nodes, Edges []string; Scopes []string } // 给增量 Validate 和冲突检测
```

## 3. 流水线

```go
// engine/op/pipeline.go
func (p *Pipeline) Submit(ctx context.Context, op *Op) (*Result, error) {
    // 0. 结构校验：jsonschema(op.schema.json)
    if err := p.schemaCheck(op); err != nil { return nil, ErrBadRequest(err) }

    return p.store.Tx(ctx, func(s store.Store) error {
        head, err := s.Graphs().Head(op.GraphID, op.Branch)          // 读最新版本（行锁）
        if err != nil { return err }

        // 1. 版本：落后则尝试 rebase
        if op.BaseVersion != head.Version {
            missed, _ := s.Ops().Range(op.GraphID, op.Branch, op.BaseVersion+1, head.Version)
            if !Commutes(op, missed) {
                return ErrConflict(head.Version, conflictsOf(op, missed)) // → 409
            }
            op = Rebase(op, missed)                                   // 改写 id 引用、From 字段
        }

        // 2. 授权
        dec := p.authz.Check(op.Actor, ActionOf(op), op.Target, authz.Ctx{Taint: op.Taint, Mandate: op.MandateID})
        switch dec.Kind {
        case authz.Deny: return ErrForbidden(dec.Reason)
        case authz.Ask:  return p.toProposal(s, op, dec)              // 1 档或例外项 → 存提议，返回 202
        }

        // 3. 应用（在副本上）
        g := head.Graph.Clone()
        inv, touched, err := p.applier.Apply(g, op)
        if err != nil { return ErrInvalid(err) }

        // 4. 增量图检查
        if diags := schema.ValidateIncremental(g, touched, p.reg); hasError(diags) {
            return ErrInvalidGraph(diags)                             // → 422
        }

        // 5. 落库：op 日志 + 新版本（每 50 版存全文）
        v := head.Version + 1
        if err := s.Ops().Append(op, inv, v); err != nil { return err }
        if err := s.Graphs().SaveVersion(op.GraphID, op.Branch, v, g, v%50 == 0); err != nil { return err }
        s.Audit().Record(op, dec)

        // 6. 通知（事务提交后发出）
        p.afterCommit(func() {
            p.bus.Publish(GraphEvent{Kind: "op.applied", Version: v, Op: op})
            p.runs.NotifyGraphChanged(op.GraphID, op.Branch, v)       // 运行中的 run 在安全点采纳
        })
        return nil
    })
}
```

返回码映射：200 已应用｜202 已转为提议（等审批）｜409 版本冲突｜403 授权拒绝｜422 图检查不通过｜400 结构错误。

## 4. 版本、乐观锁与自动 rebase

每个分支有单调递增的 `version`。客户端提交时带 `base_version`：

```
客户端看到 v40 ──提交 op(base=40)──► 服务器 head=v42（中间有 v41、v42 两条别人的 Op）
                                       │
                         Commutes(op, [op41, op42]) ?
                          ├─ 是 → Rebase → 作为 v43 应用 → 200 {version:43, rebased:true}
                          └─ 否 → 409 {head:42, conflicts:[…], missed_ops:[op41, op42]}
```

### 4.1 可交换判定

两条 Op 可交换 ⇔ 它们的**写集合**不相交，并且没有"删除-引用"关系。

| A \ B | add_node | remove_node | move | connect | set_param | group |
|---|---|---|---|---|---|---|
| move(n) | ✔ | n∈B.IDs ✘ | 同 n：后写胜，✔ | ✔ | ✔ | n∈B ✘ |
| set_param(n,k) | ✔ | n∈B ✘ | ✔ | ✔ | 同 n,k ✘ | n∈B ✘ |
| connect(e: a→b) | ✔ | a 或 b∈B ✘ | ✔ | 同一非 multi 目标端口 ✘ | promote/demote 同端口 ✘ | a/b∈B ✘ |
| remove_node(N) | ✔ | 交集非空：幂等，✔ | — | — | — | N∩B ✘ |

```go
func Commutes(op *Op, missed []*Op) bool {
    w := WriteSet(op)
    for _, m := range missed {
        if w.Intersects(WriteSet(m)) && !benign(op, m) { return false }
        if refersTo(op, Deleted(m)) { return false }
    }
    return true
}
```

`benign` 允许的情况：两条 `move` 操作同一节点（后写者胜）、重复删除同一节点（幂等）。

### 4.2 前端处理 409

1. 把返回的 `missed_ops` 应用到本地图上。
2. 如果本地还有未确认的 Op，在新的 head 上重新生成，比如 `set_param` 的 From 改成新值。
3. 冲突仍然存在时，例如同一个参数被别人改过：用户的 Op 弹出"他人已修改为 X，是否覆盖？"；**模型的 Op 不弹窗，自动转进草稿分支**。

## 5. 草稿分支与三方合并

- 分支是轻量的：`branches(graph_id, name, base_version_on_main, head_version)`。
- 模型在 1–3 档下的修改默认进入 `draft/model-<run_or_session>`；4 档可以直接写入 main（由授权书 `scope.branch` 控制）。

### 5.1 合并算法

```
base   = 分支创建时 main 的版本
ours   = main.head
theirs = draft.head

1. 读取 base→ours 的 Op 序列 Lo，以及 base→theirs 的 Op 序列 Lt
2. 结构化 diff：
     Δo = Diff(G_base, G_ours)， Δt = Diff(G_base, G_theirs)
     Diff 的输出单元：NodeAdded / NodeRemoved / NodeMoved / ParamChanged(n,k) / EdgeAdded / EdgeRemoved / LabelChanged …
3. 对 Δt 的每个单元 u：
     若 Δo 中没有作用于同一对象的单元           → 自动采纳
     若有，且两边结果相同                        → 采纳（去重）
     若是 Move vs Move                           → 取 theirs（模型布局）或 ours（按设置，默认 ours）
     否则                                        → 冲突，进入 Resolutions 列表
4. 把采纳的单元转成 Op，作用于 G_ours → 预检 Validate
5. 冲突与预检错误一起返回给前端，用户逐条选择 ours / theirs / 手工合并
6. 用户确认后提交 merge_branch{Resolutions}，作为一条复合 Op 原子应用
```

冲突对象的粒度：节点（存在性）、`(节点, 参数键)`、边、`(节点, label)`。坐标冲突永远不阻塞合并。

## 6. 撤销与重做（服务端）

| 项 | 设计 |
|---|---|
| 存储 | `ops` 表每行都存 `inverse`；另有 `undo_stack(graph_id, branch, actor_id, seq, op_id, undone bool)`，**按操作者各自一条栈** |
| 撤销 | `POST /graphs/{id}/undo {actor}`：取该操作者栈顶未撤销的 Op（同一个 `group_id` 的多条 Op 一起撤销），把它们的 inverse 当成新 Op 提交到流水线（同样要过授权和检查），然后在栈上标记 `undone=true` |
| 重做 | 对最近撤销的一组，重新提交原 Op（rebase 到当前 head） |
| 新动作清空重做栈 | 是，只清当前操作者自己的 |
| 撤销他人的修改 | 不走 undo，改用 `revert_op{op_id}`：计算目标 Op 的 inverse 并 rebase 到当前 head；不可交换时返回 409 |
| 模型修改的撤销 | 画布上的 AI 签"撤销"= `revert_op`，授权按**用户**判定 |
| 撤销失败 | 提示原因，例如"该节点已被删除"，不报静默错误 |

## 7. 连续拖动合并（coalesce）

- 前端在 pointerdown 时生成 `coalesce_key = drag:<ulid>`，拖动过程中**最多每 250ms 提交一次** `move_nodes`，松手时再提交最后一次。
- 服务器端：如果新 Op 的 `coalesce_key` 与该操作者上一条 Op 相同，并且两次间隔小于 2s，就**原地合并**：更新上一条的 To，保留最初的 From，不增加 version 计数，只广播 `op.coalesced`。
- 这样一次拖动在历史里只占一条，撤销也只需一步。
- 数字步进拖动调值（`set_param`）、滑块同样适用。

## 8. 人与模型并发编辑的策略

| 场景 | 策略 |
|---|---|
| 模型在草稿分支，人在 main | 互不干扰；草稿顶部显示"落后 main N 个版本"，可以一键 rebase |
| 模型 4 档直接写 main，人也在改 | 照常乐观锁；模型的 Op 冲突时**自动退回草稿**，并给人发通知；人的 Op 优先 |
| 人正在拖动或编辑的节点 | 前端通过 SSE 广播 `presence {actor, editing:[nodeIds]}`；模型的编排工具 `read_graph` 会返回这些"正在编辑"的节点，角色卡要求模型回避 |
| 运行中改图 | 改动进入新版本；正在运行的 run 在安全点决定是否采纳（03） |
| 急停 | 拒绝所有 `actor.kind=model` 的 Op，返回 423 Locked |

## 9. 表结构

```sql
CREATE TABLE ops (
  graph_id     TEXT NOT NULL,
  branch       TEXT NOT NULL,
  version      INTEGER NOT NULL,          -- 应用后得到的版本
  id           TEXT NOT NULL UNIQUE,      -- ULID
  kind         TEXT NOT NULL,
  actor_kind   TEXT NOT NULL,             -- user / model / system / external
  actor_id     TEXT NOT NULL,
  mandate_id   TEXT,
  reason       TEXT,
  taint        INTEGER NOT NULL DEFAULT 0,
  group_id     TEXT,
  coalesce_key TEXT,
  target       TEXT NOT NULL,             -- JSON
  payload      TEXT NOT NULL,             -- JSON
  inverse      TEXT NOT NULL,             -- JSON（服务器计算）
  ts           TEXT NOT NULL,
  PRIMARY KEY (graph_id, branch, version)
);
CREATE INDEX ops_actor  ON ops(graph_id, branch, actor_id, version);
CREATE INDEX ops_group  ON ops(group_id);

CREATE TABLE graph_versions (
  graph_id TEXT, branch TEXT, version INTEGER,
  full     INTEGER NOT NULL,              -- 1 = 存了全文
  doc      TEXT,                          -- 全文（full=1 时）
  hash     TEXT NOT NULL,
  PRIMARY KEY (graph_id, branch, version)
);

CREATE TABLE branches (
  graph_id TEXT, name TEXT, base_version INTEGER, head_version INTEGER,
  created_by TEXT, deleted_at TEXT,
  PRIMARY KEY (graph_id, name)
);

CREATE TABLE undo_stack (
  graph_id TEXT, branch TEXT, actor_id TEXT, seq INTEGER,
  group_id TEXT NOT NULL, undone INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (graph_id, branch, actor_id, seq)
);

-- 表 proposals：结构以 10_模型自主编排.md 为准，这里不重复定义。
```

读取任意版本：找到 ≤v 的最近一个 `full=1` 快照，然后按顺序重放 `ops` 表中到 v 为止的 payload。需要缓存最近 3 个版本的内存图。

## 10. 测试要点

- **属性测试**（rapid）：随机生成一串 Op，验证 `apply(op); apply(inverse)` 之后图哈希不变；可交换的两条 Op 按任意顺序应用，结果哈希相同。
- **合并**：构造 base/ours/theirs 三方，覆盖表 4.1 中的每一格。
- **并发**：100 个 goroutine 同时提交，最终版本号连续、没有丢失的 Op。
- **coalesce**：模拟 60 次 move，历史里只出现 1 条，撤销后节点回到原位。
