# 12 测试与评测

> 两件事分开讲：**测试**回答"代码对不对"，要求确定性，在 CI 里每次都跑；**评测**回答"图和角色卡好不好"，带统计性质，按需运行或每晚运行。

---

## 1. 测试金字塔

| 层 | 范围 | 工具 | 数量级 | 每次 PR |
|---|---|---|---|---|
| L1 纯函数单测 | 类型兼容、环检测、拓扑、Op/inverse、授权矩阵、路径 ID、预算 | `go test` + testify | 数百 | ✔ |

## 2. L1/L2：纯函数与属性测试

### 2.1 必须覆盖的纯函数

```
engine/graph   : Compat(out,in) / DetectCycle / Topo / Validate 每条规则 / InferTypeVars
engine/op      : Apply / Inverse / Rebase / Merge3 / Coalesce(连续拖动合并)
engine/authz   : levelDefault 全矩阵 / evalLevel / Resolver.Effective / Intersect / Delegate
engine/sched   : Ready 判定 / 令牌桶 / 优先级
engine/obs     : Path 生成与转义 / 投影（事件 → RunView）
engine/ctxasm  : 预算分配 / overflow 策略 / inherit 透传
engine/orch    : Fingerprint 规范化 / 补丁依赖推导
```

授权矩阵用**表驱动 + 黄金文件**测试：`testdata/authz_matrix.golden.csv` 枚举 5 档 × 全部 Action × {污染 / 不污染} × {预算内 / 预算外}。改动矩阵必须同时更新黄金文件，这样 review 时能看到每一处行为变化。

### 2.2 属性（rapid）

```go
func TestOpInverse(t *testing.T) {
    rapid.Check(t, func(t *rapid.T) {
        g := genGraph(t)                       // 随机合法图
        o := genOp(t, g)                       // 在 g 上合法的随机 Op
        g2 := g.Clone(); must(op.Apply(g2, o))
        inv := op.Inverse(g, o)
        must(op.Apply(g2, inv))
        require.True(t, graph.Equal(g, g2))    // Apply ∘ Inverse = id
    })
}
```

| 性质 | 内容 |
|---|---|
| P1 互逆 | `apply(inverse(o)) ∘ apply(o) = id` |
| P2 校验闭包 | 合法图 + 通过校验的 Op ⇒ 结果仍是合法图 |
| P3 可交换 Op 的 rebase | 若 a、b 可交换：先 a 后 rebase(b) 与先 b 后 rebase(a) 结果一致 |
| P4 三方合并 | `merge(base, x, x) = x`；`merge(base, base, y) = y` |
| P5 授权单调 | 档位升高时，任何动作的结果都不会更严（allow → ask → deny 的顺序不倒退） |
| P6 收窄 | `Intersect(p, c) ⊆ p` |
| P7 调度安全 | 任意时刻 running 节点的所有必填输入都已就绪；资源池占用 ≤ 配额 |
| P8 投影确定性 | 同一事件序列投影两次，结果完全相同 |
| P9 指纹稳定 | 打乱补丁里 Op 的顺序、改动理由，fingerprint 不变 |

## 3. L3：执行器测试与 Fake LLM

### 3.1 Fake LLM

```go
type FakeLLM struct {
    Script []FakeTurn     // 按顺序返回
    Rec    *Cassette      // 或从录制带回放
    Calls  []llm.Req      // 记录收到的请求，用于断言上下文内容
}
type FakeTurn struct {
    Match     func(llm.Req) bool   // 可选：按请求内容匹配
    Text      string
    ToolCalls []llm.ToolCall
    JSON      any                  // 结构化输出
    Err       error                // 模拟 429 / 超时 / 坏 JSON
    Delay     time.Duration        // 配合虚拟时钟
    Usage     llm.Usage
}
```

每个 Agent 类执行器至少覆盖以下场景：

- 正常结构化输出
- 坏 JSON → 修复成功
- 坏 JSON → 修复失败 → 重试
- 429 → 退避重试
- 超时
- 工具调用多轮
- 输出不符合 schema → 走升级端口
- 被取消

### 3.2 录制 / 回放（Cassette）

```
HARNESS_LLM_MODE=record   真实调用，并把 (规范化请求哈希 → 响应) 写入 testdata/cassettes/<suite>.jsonl
HARNESS_LLM_MODE=replay   只读录制带；未命中时失败（CI 默认）
HARNESS_LLM_MODE=live     真实调用，不录制（评测时用）
```

- 规范化请求：去掉时间戳和 ULID，排序 tools 和 JSON 键，再计算哈希。这样提示词里只有无关字段变化时仍能命中。
- 录制带进 git，但要过脱敏检查：CI 里扫描是否包含密钥模式。
- 提示词有实质改动导致未命中时，开发者在本地 `make record SUITE=xxx` 重新录制，PR 里能看到录制带的 diff。
- 好处：CI 零模型成本，结果确定，离线也能跑。

### 3.3 Fake Tool

工具层也一样：`FakeTool{Responses, Latency, FailEvery}`，用来测试幂等键（同一个键只执行一次）、限流排队和污染标记的传播。

## 4. L4/L5：调度确定性与崩溃恢复

### 4.1 虚拟时钟

引擎里所有和时间有关的代码都只通过 `clock.Clock` 接口取时间：`Now`、`After`、`NewTimer`、令牌桶、超时、重试退避、心跳。

```go
func TestLoopThreeRounds(t *testing.T) {
    clk := clock.NewFake(t0)
    eng := testEngine(t, WithClock(clk), WithLLM(fakeFromCassette("loop3")), WithSeed(42))
    run := eng.Start(ctx, loadGraph("testdata/graphs/闭环迭代.json"))
    clk.RunUntilIdle()                       // 推进虚拟时间，直到没有可运行的工作
    v := eng.View(run.ID)
    require.Equal(t, "done", v.Status)
    require.Equal(t, 3, v.Nodes["根图/闭环迭代"].Rounds)
    golden.Assert(t, v.Timeline, "loop3.timeline.golden.json")   // 时间线快照
}
```

- 调度器内部的并发通过 `WithSeed` 控制 goroutine 的唤醒顺序（测试模式下用单线程事件循环 + 确定性的随机打乱），所以同一个 seed 每次得到的事件序列完全一致。
- 场景库 `testdata/graphs/` 至少包括：线性、扇出 + 汇合（等全部 / 等 K 个 / 超时）、循环（达成 / 达到最大轮数 / 无进展）、嵌套子图、人工挂起、限流背压、取消传播、运行中改图在安全点生效、预算耗尽、急停。

### 4.2 崩溃恢复

```go
func TestCrashRecoveryAt(t *testing.T) {
    for _, cut := range interestingCuts(t) {          // 事件序号集合：每类事件的前后各一处
        t.Run(fmt.Sprint(cut), func(t *testing.T) {
            dir := t.TempDir()
            p1 := startHarnessd(t, dir, CrashAfterEvent(cut))  // 写完第 cut 条事件后 os.Exit(137)
            p1.Wait()
            p2 := startHarnessd(t, dir)                        // 同一个数据目录重启
            v := p2.WaitRun(runID)
            require.Equal(t, "done", v.Status)
            require.Equal(t, 1, sideEffects.Count("send_email")) // 有副作用的工具只执行一次
            require.Equal(t, refView, normalize(v))              // 与不崩溃的参考运行一致
        })
    }
}
```

需要验证的不变量：
- 运行能完成
- 有副作用的工具恰好执行一次（幂等键）
- 结果与参考运行一致（忽略时间戳）
- 审批挂起的节点在重启后仍是 waiting
- 急停状态在重启后保持

## 5. L6–L9

### 5.1 API 契约

- 所有请求和响应体都由 `schema/` 下的 JSON Schema 描述。测试中间件 `contract.Middleware` 在测试环境里对每个请求和响应都做校验，校验不通过就让测试失败。
- `packages/protocol`（TS）由同一份 schema 生成。CI 会检查重新生成后 git diff 为空，以此确保两端类型不漂移。
- SSE 事件也逐条按 `run-event.schema.json` 校验。

### 5.2 前端 e2e（Playwright）

| 流程 | 断言 |
|---|---|
| 新建图 → 拖入节点 → 连线 → 运行 | 节点依次变为 running → done；时间线出现条段 |
| 类型不兼容连线 | 出现红色预览和原因文案；松开后没有生成连线 |
| 撤销 / 重做 | 图恢复；Op 日志条目变灰 |
| 两个浏览器同时编辑 | 冲突一方收到提示，可以合并 |
| 1 档模型提议 | 幽灵节点出现；逐条采纳后节点变实 |
| 人工审批 | 节点挂起；在对话中批准后继续运行 |
| 急停 | 顶栏变为急停色；运行中的节点全部变为 cancelled |
| 断网重连 | SSE 恢复，事件不丢失（按 seq 连续） |
| 浅色 / 深色视觉回归 | `toHaveScreenshot`，阈值 0.1%；浅色为必跑，深色为每晚 |

e2e 使用挂载了 harness 的宿主服务加 replay 模式的 Fake LLM，用 `make e2e` 一键启动。

### 5.3 性能压测

| 场景 | 目标 |
|---|---|
| 前端：200 节点 / 300 连线，拖动和缩放 | ≥ 55 fps（Playwright trace 统计帧时长） |
| 前端：1000 节点 | ≥ 30 fps，开启视口裁剪 |
| 前端：每秒 100 条运行事件 | 主线程长任务 < 50ms |
| 后端：调度 1000 节点的图（Fake LLM 零延迟） | 调度开销 < 2s |
| 后端：20 个并发运行 × 每个 50 节点 | p95 事件写入 < 20ms，内存 < 1GB |
| 后端：100 个 SSE 客户端 | 推送延迟 p95 < 100ms |
| 后端：Op 提交 | p95 < 30ms（SQLite WAL） |
| 授权 Check | < 50µs |

## 6. 评测框架

### 6.1 评测集格式（`evals/<name>/cases.jsonl`）

```json
{"id":"price-001","inputs":{"goal":"调研 A/B/C 三家企业版定价"},
 "constraints":{"币种":"CNY","计费周期":"年"},
 "expect":{"criteria":[{"id":"c1","rule":"count(result.companies) >= 3"},
                       {"id":"c2","rule":"all(result.prices, .source != '')"}],
           "judge":{"rubric":"rubrics/定价报告.md","min":0.7}},
 "tags":["定价","不完整数据"]}
```

- `rule`：确定性检查（expr 表达式）
- `judge`：可选，由评审模型按评分表打分，评审使用**和被测对象不同厂商的模型**
- 每条用例可以重复运行 k 次（默认 3），用来降低随机性

### 6.2 评测子图

评测本身也用积木拼成，作为内置模板 `eval/compare@1`：

```
资源(评测集) → 扇出[items=cases × variants, concurrency=4] {
    子图引用[ref ← variant.graph]       ← 被测的图（或同一张图换角色卡）
      → 验收：规则检查 + 评审 Agent
} → 聚合[group by variant] → 报告
```

### 6.3 A/B 对比

```bash
harnessctl eval compare \
  --suite evals/定价 \
  --a graph:g1@v12 --b proposal:p7 \
  --repeat 3 --budget-cny 50
# 也可以比较角色卡：--a rolecard:执行者@1 --b rolecard:执行者@2
```

报告：

| 指标 | A | B | Δ | 显著性 |
|---|---|---|---|---|
| 通过率 | 0.78 | 0.92 | +0.14 | 配对 bootstrap，p<0.05 |
| 评审均分 | 0.71 | 0.80 | +0.09 | |
| 编造率（抽检不一致） | 0.12 | 0.03 | −0.09 | |
| 耗时 p50 | 6:12 | 4:05 | −34% | |
| tokens 均值 | 412k | 438k | +6% | |
| 费用 | ¥3.10 | ¥3.30 | +6% | |

报告保存为 `eval_runs` 记录，提议页面可以直接附上这份报告。

### 6.4 回归门槛

- 修改内置模板、内置角色卡或上下文装配逻辑的 PR，CI 会对相关评测集运行 **replay 模式**的快速评测。这一步只检查结构化输出合法、规则检查结果不倒退，成本为 0。
- 每晚运行 **live 模式**的完整评测（预算上限 ¥200），通过率比基线下降 > 5% 时发告警。
- 角色卡在推广到默认之前，必须有一份 A/B 报告，且通过率不低于旧版。

## 7. CI 门禁

| 阶段 | 内容 | 失败即阻断 |
|---|---|---|
| lint | `golangci-lint`、`eslint`、`tsc --noEmit`、schema 格式检查 | ✔ |
| codegen | 重新生成 Go/TS 类型，diff 必须为空 | ✔ |
| unit | L1 + L2（rapid 200 例）+ L7 | ✔ |
| exec | L3 + L4 | ✔ |
| crash | L5 抽样（10 个切点） | ✔ |
| contract | L6 | ✔ |
| e2e-smoke | L8 冒烟（6 条流程，浅色主题截图） | ✔ |
| eval-replay | 相关评测集 replay | ✔（仅在相关文件改动时运行） |
| secrets | 扫描录制带、日志样例、测试数据中的密钥 | ✔ |
| nightly | L5 全量、L8 全量（两套主题）、L9 压测、live 评测 | 告警，不阻断 |

覆盖率要求：`engine/authz`、`engine/op`、`engine/graph` ≥ 90%；其他引擎包 ≥ 75%。
