# 10 模型自主编排

> 包：`engine/orch`（编排者执行器、补丁、提议、展开、优化），复用 `engine/op`（应用补丁）、`engine/authz`（判定）、`engine/graph`（图检查）。
> 核心原则：**模型改图和人改图走同一条 Op 流水线**。编排能力不是一种特殊权限，而是一个普通节点组合加上一组图操作工具。

---

## 1. 三种介入时机

| 时机 | 触发 | 产物 | 默认档位 |
|---|---|---|---|
| 设计时 | 用户在对话里描述需求 / 选中节点"问模型" | GraphPatch → 提议或直接生效 | 1 建议 |
| 运行时 | 编排者节点在运行中被执行 | 子图（以 GraphPatch 表示）→ 在安全点挂载并执行 | 按授权书 |
| 运行后 | 用户点击"优化"或规则自动触发 | 优化补丁 + 评测对比报告 | 1 建议 |

三种时机共用同一个执行器 `orch.Orchestrator` 和同一套工具；区别只在输入（需求 / 运行状态 / 留痕摘要）和补丁落地的方式。

## 2. GraphPatch

### 2.1 Schema（`schema/graph_patch.schema.json`）

```json
{

  "type": "object",

    "ops": {

      "items": { "$ref": "op.schema.json#/$defs/Op" }
    },
    "rationale": { "type": "string", "maxLength": 2000, "description": "整体理由" },
    "op_reasons": {
      "type": "object", "description": "op.id → 单条理由",
      "additionalProperties": { "type": "string", "maxLength": 400 }
    },
    "expected_effect": {
      "type": "object",
      "properties": {
        "quality":  { "type": "string" },
        "latency":  { "type": "string" },
        "cost":     { "type": "string" },
        "risk":     { "type": "string" }
      }
    },
    "origin": { "type": "string", "enum": ["design", "runtime", "optimize"] },
    "parent_patch": { "type": ["string", "null"] },

```

Op 中新增节点用**临时 ID**（`tmp:1`、`tmp:2`），后续 connect 可以引用这些临时 ID。应用时统一换成 ULID，并返回映射表，供前端把幽灵节点替换为真实节点。

## 3. 编排者节点

### 3.1 节点组合（不是新的原子节点）

```
[上下文装配: 编排者配方]
   ├─ in: 需求 / 运行状态摘要 / 留痕摘要
   ├─ in: 当前图（read_graph 的精简视图）
   └─ in: 可用节点定义列表摘要
        ↓ context
[Agent: 编排者]  output_schema = GraphPatch@1   tools = 图操作工具集
        ↓ result (GraphPatch)
[子图引用: ref ← 端口]   ← 仅运行时展开时需要；设计时直接交给 Op 流水线
```

### 3.2 执行流程（Go 伪代码）

```go
func (o *Orchestrator) Run(rc exec.RunCtx, in exec.Inputs) (exec.Outputs, error) {
    sess := o.newToolSession(rc)                   // 维护草稿图：工具调用先改草稿
    resp, err := rc.LLM().Run(rc, agentReq(in, sess.Tools()))  // 多轮工具调用循环，max_inner_turns
    if err != nil { return nil, err }

    patch := sess.Finalize(resp)                   // 草稿 diff 当前图 → GraphPatch，算 fingerprint
    if dup := o.seen(rc.RunID(), patch.Fingerprint); dup {
        return nil, rc.Escalate("重复补丁", patch)   // 防止原地打转
    }
    if diags := graph.Validate(sess.Draft()); len(diags) > 0 {
        return nil, rc.Retry(feedback(diags))      // 把图检查错误喂回模型，最多 2 次
    }
    dec := rc.Authz(authz.Request{Act: authz.ActApplyPatch, Target: tgt(patch), Patch: ptr(patch.Stats(g))})

    switch {
    case dec.Effect == authz.Deny:
        return nil, rc.Fail(ErrDenied{dec})
    case dec.Propose:                              // 1 档 / 2 档范围外
        id := o.proposals.Save(patch, dec)
        rc.Emit(Event{Kind: "proposal.created", Data: id})
        return exec.Out("patch", patch, "status", "proposed"), nil
    case dec.Effect == authz.Ask:
        if ok := rc.Ask(approvalFor(patch, dec)); !ok { return nil, rc.Fail(ErrRejected) }
        fallthrough
    default:
        return o.apply(rc, patch)                  // 设计时：提交 Op；运行时：安全点挂载
    }
}
```

**草稿图**：工具调用（add_node、connect……）先作用在内存里的草稿副本上，每次调用立即做局部校验并把结果返回给模型。模型调用 `finish` 或停止调用工具时，再对比草稿和原图生成补丁。好处是模型可以试错，而真实的图只会收到一次原子提交。

## 4. 图操作工具集（暴露给模型）

所有工具都作用于**草稿图**。参数里的节点可以用 ULID、临时 ID（`tmp:n`）或 `path:根图/闭环迭代/执行池` 这类路径引用。每次调用的返回都很短（≤ 400 tokens），包括：结果、受影响的节点 ID、校验警告。

| 工具 | 风险 | 说明 |
|---|---|---|
| `read_graph` | L0 | 读取图的精简视图 |
| `read_node` | L0 | 读取单个节点的完整参数和端口 |
| `list_nodedefs` | L0 | 列出可用节点定义的摘要 |
| `get_nodedef` | L0 | 读取单个节点定义的参数 schema |
| `list_types` / `check_compat` | L0 | 查询类型、判断端口能否连接 |
| `add_node` | 改图 | 新增节点 |
| `remove_node` | 改图 | 删除节点及其连线 |
| `connect` / `disconnect` | 改图 | 连线 / 断线 |
| `set_param` | 改图 | 设置参数 |
| `promote_param` | 改图 | 把参数转为端口 |
| `group` | 改图 | 把一组节点封装为子图 |
| `read_trace_summary` | L0 | 运行后优化用：读取留痕摘要 |
| `run_subgraph` | 运行 | 在沙箱副本中试跑草稿中的一个子图（受预算约束） |
| `request_elevation` | 授权 | 申请提权 |
| `propose` / `finish` | — | 结束编辑。`propose` 强制以提议形式提交；`finish` 按授权决定提议还是直接生效 |

## 5. 提议（Proposal）

### 5.1 存储

```sql
CREATE TABLE proposals (
  id           TEXT PRIMARY KEY,
  graph_id     TEXT NOT NULL,
  branch       TEXT NOT NULL DEFAULT 'main',
  base_version INTEGER NOT NULL,
  patch        TEXT NOT NULL,          -- GraphPatch JSON
  actor        TEXT NOT NULL,          -- Principal JSON
  origin       TEXT NOT NULL,          -- design | runtime | optimize
  status       TEXT NOT NULL,          -- open | partially_applied | applied | rejected | stale
  decisions    TEXT NOT NULL DEFAULT '{}', -- op_id → accepted|rejected
  created_at   TEXT NOT NULL,
  decided_at   TEXT
);
```

### 5.2 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/graphs/{id}/proposals?status=open` | 列出提议 |
| GET | `/proposals/{pid}/preview` | 返回 `ghost_graph`：在当前图上叠加补丁后的视图，每个元素都标注 `ghost: add|remove|modify`，以及 `old/new` 值和理由 |
| POST | `/proposals/{pid}/decide` | `{accept: [op_id...], reject: [op_id...]}`，可以逐条处理；被采纳的 Op 走正常 Op 流水线，actor 记为模型、approver 记为用户 |
| POST | `/proposals/{pid}/accept_all` / `reject_all` | 全部采纳 / 全部拒绝 |

- **依赖处理**：采纳 `connect tmp:1.out → n5.in` 时，`add_node tmp:1` 会被自动一起采纳；拒绝 `add_node` 时，依赖它的连线也被一并拒绝。依赖关系由补丁里的临时 ID 引用自动推导。
- **过期**：图的版本前进后，提议会尝试 rebase（规则见 08 号文档）。rebase 失败就标记为 stale，前端显示"已过期，请让模型重新生成"。
- SSE：`proposal.created / updated / decided`。前端收到后渲染幽灵节点和提议栏。

## 6. 运行时动态展开

### 6.1 流程

```
编排者节点执行（运行中）
  ① 生成 GraphPatch（origin=runtime，target_path=子图引用的内部路径）
  ② graph.Validate(补丁应用后的子图)         —— 失败：错误反馈给模型重试（≤2 次），仍失败则升级
  ③ authz.Check(ActApplyPatch, Patch stats) —— deny / ask / allow
  ④ 写事件 orch.expanded {patch_id, patch, graph_version_before, after}   ← 回放依据
  ⑤ 等到安全点：子图引用节点在下游被调度时挂载（不改动正在运行的节点）
  ⑥ 子图引用以 ref=生成的子图 执行；预算从父级划拨
```

```go
func (o *Orchestrator) applyRuntime(rc exec.RunCtx, p *GraphPatch) (exec.Outputs, error) {
    sub := rc.Snapshot().Subgraph(p.TargetPath).Clone()
    if err := op.ApplyAll(sub, p.Ops); err != nil { return nil, err }
    rc.Emit(run.Event{Kind: "orch.expanded", Data: run.Expanded{
        PatchID: p.ID, Patch: p, Subgraph: sub, Fingerprint: p.Fingerprint,
    }})
    return exec.Out("ref", graph.InlineRef(sub)), nil     // 交给下游的子图引用节点
}
```

### 6.2 可复现：回放规则

- 运行的事件日志里，`orch.expanded` **保存完整的生成子图**，不只是补丁。
- 回放（`POST /runs/{id}/replay`）时，编排者执行器检测到 `rc.Replaying()`，不调用模型，直接读取对应 `node_path` 和 `attempt` 的 `orch.expanded` 事件，返回同一张子图。
- 审批结果也从日志里读取，不会重新弹出审批。
- 生成的子图同时保存为图版本（`graph_versions.kind = 'generated'`），在前端「版本」面板可以查看和比较。

### 6.3 安全点挂载

运行时生成的子图**只会挂载到"尚未开始执行"的子图引用节点上**。如果模型想修改的是正在运行的循环，就挂在循环的下一轮：循环执行器在每轮开始前检查 `pendingPatches[loopPath]`。这样就不会出现"正在执行的节点被换掉"的情况。

## 7. 运行后优化

```
POST /runs/{id}/optimize  {goal: "降低耗时，保持质量", budget_tokens: 200000}
  ① obs.TraceSummary(run)      → 每个节点：耗时、tokens、失败/重试、等待、抽检结果（≤ 3k tokens）
  ② 编排者（origin=optimize）   → 候选 GraphPatch（1 份或多份）
  ③ 评测：eval.Compare(旧图, 新图, 评测集)  —— 使用 12 号文档的评测子图
  ④ 输出报告：分数 / 耗时 / tokens / 成本 对比 + 补丁 → 作为提议，等待用户采纳
```

`TraceSummary` 结构：

```go
type NodeSummary struct {
    Path      string   `json:"path"`
    Type      string   `json:"type"`
    Runs      int      `json:"runs"`
    Fails     int      `json:"fails"`
    P50S      float64  `json:"p50_s"`
    P95S      float64  `json:"p95_s"`
    Tokens    int64    `json:"tokens"`
    WaitS     float64  `json:"wait_s"`      // 排队/限流/审批等待
    Notes     []string `json:"notes"`       // 如 "抽检 3 条不一致"、"限流排队 8 次"
}
```

评测报告的格式见 12 号文档 §6。

## 8. 防失控

| 风险 | 限制 | 默认值 | 位置 |
|---|---|---|---|
| 图膨胀 | 单个补丁最多新增节点数 | 30 | 授权书 MaxNodes / 内核上限 200 |
| 图膨胀 | 一次运行中生成的节点总数 | 300 | run 级计数器 |
| 递归 | 子编排者嵌套深度 | 3（内核上限 8） | 授权书 MaxDepth |
| 烧钱 | 编排预算（含 run_subgraph 试跑） | 父级划拨 | 预算账户 |
| 原地打转 | 重复补丁检测：规范化 ops 后计算 fingerprint | 同一 run 内重复即升级 | orch.seen |
| 原地打转 | 连续 N 次补丁评测分数未提升 | 2 次即停 | optimize 循环 |
| 自修改 | 修改编排者自身所在层或上层 | 3 档及以下 deny/ask，4 档 allow | ActSelfModify |
| 自修改 | 修改授予自己的授权书 | 永远 deny | authz |
| 内部工具循环 | 单次编排的工具调用轮数 | 30 | Agent limits |

**fingerprint 的规范化**：
- 去掉临时 ID 编号、理由和坐标
- 按 (kind, target, param) 排序
- 数值参数分桶，例如并发 3 和 4 视为相近

规范化之后再计算 sha256。这样模型"换种说法提同一个补丁"也会被识别出来。

## 9. 编排者角色卡示例

```yaml
role_card: 编排者@1
identity: 你是流程编排者。你通过图操作工具修改一张多 Agent 流程图，目标是让流程以更低成本稳定达成验收标准。
mission: 根据输入（需求 / 运行状态 / 留痕摘要），产出一份最小、可解释、可撤销的图补丁。
method:
  - 先 read_graph 和 list_nodedefs，弄清现状和可用积木；不要凭记忆假设节点参数。
  - 优先改参数，其次加节点，最后才改结构；能用现有子图就不新建。
  - 每个修改都写一句理由，说明它针对哪个问题、预期改善什么。
  - 每次 connect 前不确定时先 check_compat；工具返回失败时按 hint 修正，不要重复同样的调用。
  - 涉及 L2 以上工具、更换大模型、删除节点时，在 rationale 里明确写出风险。
  - 运行后优化：只针对留痕摘要里有证据的问题动手，并引用证据（节点路径 + 指标）。
good_output: 补丁的 op 数尽量少；每条 op 都有理由；补丁应用后图检查无错误；expected_effect 写清质量、耗时、成本的预期变化。
boundaries:
  - 不修改验收标准和目标（只读字段）。
  - 不修改授予自己的授权书；超出授权时用 request_elevation 申请，不要绕过。
  - 不为了"看起来更完整"而加节点。
when_stuck: 需求有歧义或缺少关键信息时，finish 时设 force_proposal=true，并在 rationale 中列出需要用户确认的问题。
vars: [需求, 运行状态, 留痕摘要, 当前图摘要, 节点定义摘要]
fit_models: [大模型]
```
