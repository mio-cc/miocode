# 项目树索引 v0.5

> 整个项目按"作用域 → 模块 → 子模块 → 叶子"拆成一棵树，**每个节点对应一份文档**。上层文档定边界和约束，下层只写细节，不能推翻上层。
> 实施模型拿到任何一个叶子，只读"这个叶子 + 它的祖先链 + 它引用的契约"就能动手，不需要猜。
> 本文件只是索引（目录），机器可读版本在 [树索引.json](树索引.json)，两者必须一致。各节点写到哪一步以**文档文件头的"状态"**为准，汇总进度运行 `python tools/check_tree.py`。
> **接力写作先读 [00_从这里开始.md](00_从这里开始.md)。**

## 2. 我替你补上的部分

你提到的是：项目结构、项目规范、前端 UI/UX 规范、后端。下面这些你没提，但按经验缺了会在实施阶段出问题，我都加进去了：

- **AI 实施者守则（G.02）**：后面是模型来写代码，它最容易出的问题是"自作主张"：顺手改接口、引入没登记的库、文档没写就自己发明。这一节专门给模型定硬规矩，包括遇到矛盾必须停下上报、派任务时必须附带哪些文档。这是防止偏移最直接的一层。
- **契约层单独成一枝（C）**：前端、后端、内核都要用同一套数据格式（图、节点、事件、错误码）。如果各自在自己的文档里写，一定会写出三个版本（旧文档里已经出现过 Executor 接口三版、运行状态两版）。所以把它提出来先写，其他分支只引用、不重写。
- **决策记录 ADR（P.08）**：把"为什么这么选"记下来。以后有模型或有人想改技术栈、改布局，必须先新开一条 ADR 说清理由，不能直接改。
- **术语表（P.06）**：同一个东西只能有一个名字（比如"子图 / 子系统 / 子流程"必须统一）。名字一乱，模型就会以为是两个东西。
- **安全与隐私（S）**：这个产品会调用模型、执行工具和代码、加载别人写的扩展。本机服务也有被网页攻击的风险（比如 DNS 重绑定）。这些必须单独写清楚，不能散在各处。
- **质量与测试（Q）**：每个实施叶子的"验收标准"都要落到具体测试上。测试规则统一写在这里，叶子文档只引用。包括"CI 里不调用真模型"这类容易漏的规则。
- **构建、发布与运维（O）**：怎么打包成一个文件发给用户、怎么自动更新、用户数据放哪、怎么备份、出问题时怎么一键收集日志。
- **扩展生态（X）**：你的理念是"可扩展、高度自定义"，但需要写清楚别人具体能扩展什么、怎么写，否则只停留在口号上。
- **内置模板（T）**：模板既是给用户的示例，也是最真实的端到端测试用例。
- **用户文档（D）**：给最终用户看的快速开始、概念讲解、排错手册。
- **用户流程（U.19）**：把关键任务（第一次运行、用对话改图、审批、急停、打开子图……）一步一步画出来。界面实现和端到端测试都按它来。
- **完成定义 DoD（G.14）、错误码（G.13 / C.11）、日志规范（G.12）、配置规范（G.11）**：这类"小规矩"如果不统一，每个模块的写法都会不一样，后期很难收拾。
- **待决问题与已知不一致（P.09）、旧文档映射（R.04）**：把旧文档里已经发现的冲突集中登记，写明以哪一份为准；每份旧文档都对应到新树上的节点，确保旧内容不会丢。

## 3. 规则

### 3.1 编号
- 一级用字母：`P` 总纲、`G` 工程规范、`C` 契约、`E` 内核、`B` 后端、`W` 前端实现、`U` UI/UX 规范、`S` 安全、`Q` 质量、`O` 运维、`X` 扩展、`T` 模板、`D` 用户文档、`R` 附录。
- 下级用两位数字逐级追加：`E` → `E.14` → `E.14.02` → `E.14.02.01`。
- 编号一旦分配就不改，也不复用。删除的节点标"已废弃"并保留编号；新增节点只能往后追加。
- 文档之间引用一律写编号，例如"见 `C.05.02`"，不要写"见上面那份"。

### 3.2 文件位置
- 根目录 `sj/项目树_v0.5/`。一级分支是一个文件夹；有下级的节点也是一个文件夹，节点本身的文档放在同名文件夹里；叶子是单独的 `.md` 文件。
- 例：`E_内核_engine/E.14_exec_执行器/E.14.02_Agent/E.14.02.01_工具调用循环.md`。
- 下表"文件"列是每份文档的确切路径，生成时照着建。
- 根目录里不属于任何节点、允许存在的文件只有：`00_从这里开始.md`（接力入口）、`00_树索引.md`、`树索引.json`、`01_文档模板.md`、`接力日志.md`、`tools/`（检查脚本）。其他文件一律放进对应节点。

### 3.3 文档类型
| 类型 | 用在哪 | 必须有的内容 |
|---|---|---|
| 总则 | 一级分支 | 这一枝管什么、不管什么；下级清单；整枝共同约束；和其他分支的接口 |
| 规范 | 只定规则、不直接产出代码的节点 | 规则逐条编号（如 `G.04.01-R3`）；正例和反例；怎么检查（最好能自动检查） |
| 实施 | 要产出代码的节点 | 职责；明确不做什么；上下游接口；继承的上级约束；不变量；错误处理；验收标准；叶子另附**实施卡**（要建的文件、函数签名、数据结构、测试用例、禁止事项） |
| 说明 | 背景、指南、用户文档 | 读者是谁；要讲清楚的问题；示例 |

每份文档开头统一写：编号、标题、类型、上级、状态（待写 / 草稿 / 已审 / 冻结）、素材来源。完整模板见 [01_文档模板.md](01_文档模板.md)。

### 3.4 写作顺序
下层依赖上层，被引用最多的先写：

| 批次 | 内容 | 原因 |
|---|---|---|
| 1 | `P` 总纲、`G.01` 文档体系、`G.02` AI 实施者守则、`P.06` 术语表 | 定规矩和用词，后面所有文档都按它写 |
| 2 | `C` 契约层全部 | 前端、后端、内核都依赖它 |
| 3 | `G` 其余、`U` UI/UX 规范、`S` 安全 | 规则类，实施类文档要引用 |
| 4 | `E` 内核、`B` 后端、`W` 前端实现 | 主体实施文档，可以多个模型并行写 |
| 5 | `Q`、`O`、`X`、`T`、`D`、`R` | 收尾；最后整树做一遍一致性检查 |

每写完一批，我会把这一批和已写的上层对照检查一遍，确认没有冲突再写下一批。
