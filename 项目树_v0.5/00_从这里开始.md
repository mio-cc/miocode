# 从这里开始（接力入口）

> **任何一棒（模型或人）开始写文档之前，先读完这一页。** 这是项目树唯一的入口（`G.01-R23`）。
> 本页只写"怎么接力"。项目是什么、规则是什么，都在树里，这里只给指路。

## 1. 开工三步（每一棒都要做，按顺序）
1. **读完本页。**
2. **读 [接力日志.md](接力日志.md) 最上面一条**：上一棒停在哪、"进行中"写了什么、"下一步"是什么、有哪些遗留问题。日志里写了"进行中"的部分，先确认它是否写完（看文件头状态、看正文有没有写到最后一节），没写完就从那里接着写。
3. **在 `项目树_v0.5` 目录运行：**
   ```
   python tools/check_tree.py           # 进度、错误、警告
   python tools/check_tree.py --next    # 接下来该写哪些
   ```
   有错误先修错误，再写新文档。

## 2. 这个项目是什么（30 秒版）
Anywhere Door：装在本机的多 Agent"积木编排台"。画布居中，底部对话框，左右侧栏；人和模型用同一套操作（Op）改图，档位决定模型能改多少，急停只有人能解除；子图可以无限嵌套；运行靠事件日志续跑和回放。

详细的以这几份为准，**每一棒都要读**，不管写哪一枝：
| 文档 | 为什么必读 |
|---|---|
| `P.01` 愿景与定位、`P.02` 范围与非目标 | 做什么、不做什么 |
| `P.04` 核心理念与系统不变量 | 任何文档都不能违反的 INV-01…24 |
| `P.06` 术语表 | 唯一用词来源；新词先登记再用 |
| `P.09` 待决问题与已知不一致 | 已经裁决的冲突（K）和还没定的问题（Q）；写到相关内容时照它做 |
| `G.01` 文档体系规范（含 §3.6 接力规则）、[01_文档模板.md](01_文档模板.md) | 怎么写、怎么编号、文件头怎么填 |
| `G.02` AI 实施者守则、`G.02.05` 禁止事项总表 | 写实施卡时要落实的硬规则 |

## 3. 写一份（或一组）文档的流程
1. **领取**：在 `接力日志.md` 本棒条目的"进行中"里写下要写的范围（一次领一个子树，例如 `W.06` 及其下级）。
2. **收集约束**（缺这一步就会出现"漏读上层"）：
   - `python tools/check_tree.py --refs <编号>`：列出全树里引用这个编号的每一处。**每一处都是对它的要求，逐条落实**（例：B、C、E 文档里写着"前端每 250ms 提交一次（`W.05`）"，写 `W.05` 时就必须有这一条）。
   - 读祖先链全文（一级总则 → … → 父节点）。
   - 读 `00_树索引.md` 里该节点的"写什么""素材"两列；素材缩写见索引 §4 开头。
   - 读它要引用的 `C` 契约、`U` 规范、`B` 接口、`E` 接口。旧素材（引擎计划、设计规范 v0.3、demo v0.4）只作参考，和项目树冲突时以项目树为准。
3. **写**：
   - 按 [01_文档模板.md](01_文档模板.md) 对应类型写；文件放在索引"文件"列的确切路径。
   - 文件头：编号、类型、上级、下级、状态写"草稿"、素材、最后修改写当天日期。
   - 只用 `P.06` 的词；需要新词，先登记到 `P.06` 再用（`P-R3`）。
   - **发现上层矛盾就停下**：先修上层或登记 `P.09`（能裁决写 K，不能裁决写 Q 并告诉用户），再继续写下层（`G.01-R28`）。不要在下层"绕过去"。
4. **检查**：`python tools/check_tree.py` 没有错误。
5. **记录**：每写完一个子树，或最多 10 份，就更新一次接力日志（`G.01-R25`）。**不要等到最后**——上下文随时可能被打断，没记下来的进度等于没做。

## 4. 检查脚本说明
| 命令 | 用途 |
|---|---|
| `python tools/check_tree.py` | 各枝进度（总数 / 待写 / 草稿 / 已审 / 冻结）；错误（E1–E7）和警告（W1） |
| `python tools/check_tree.py --refs W.07.05` | 全树里引用某个编号的地方 |
| `python tools/check_tree.py --next` | 按批次顺序列出接下来该写的节点 |
| `python tools/check_tree.py --quiet` | 只看汇总和错误 |

检查项：文件头字段、多余文件、`00_树索引.md` 与 `树索引.json` 一致、引用的编号存在、术语（`tools/术语检查.json` 里登记的、不会误报的"不要叫"词）、demo 最新版本已回写、实施类叶子有实施卡。

## 5. 收工（或感觉上下文快用完时）必须做
1. `python tools/check_tree.py` 没有错误。
2. 在 `接力日志.md` 最上面写完本棒记录（模板在日志顶部）：完成了什么、进行中停在哪、下一步、遗留问题 / 待用户确认的事。
3. 如果改了批次级进度，更新 `00_树索引.md` §6（只写批次级，不抄数字）。
4. 同步到 GitHub（`mio-cc/miocode`，main 分支）：用户电脑上接了 Codex 时，让 Codex 在 `sj` 目录执行 `git add -A`、`git commit`、`git push`（提交信息写本棒编号和范围）；没接时提醒用户双击 `sj/同步到git.bat`。推送后在接力日志的 git 一栏写提交号。

## 6. demo 回写协议（这次出问题的根源）
demo 是设计原型，规范才是依据。demo 改了而规范没跟上，下一棒就会照着过时的规范写。所以：
1. demo 每出一个版本：在 demo 目录的 `README.md` 版本记录里加一行，并更新"最新版本"。
2. **同一棒内**回写：受影响的 `U` 规范、`C` 契约、`P.06`（新词）、`P.09`（新的裁决或待决）、`00_树索引.md` 与 `树索引.json` 里受影响叶子的名称和说明、`U.24` 待修清单的状态。
3. 在下面 §7 回写记录里加一行：demo 版本 → 回写了哪些编号。
4. `check_tree.py` 会比对 demo README 的最新版本和 §7，没登记就报错（E7）。

## 8. 常见的坑
| 坑 | 正确做法 |
|---|---|
| 照着根目录 `交接说明.md` 的阅读顺序读 | 那份是给"写代码"的模型的旧说明（v0.4）。写文档按本页 |
| 以为 `00_树索引.md` 顶部或 §6 的数字是准的 | 以文件头状态和 `check_tree.py` 输出为准 |
| 只读了要写的那份的上级就动笔 | 必须跑 `--refs`；别的分支里经常写着对它的要求 |
| demo 里有、规范里没有，就直接写进文档 | 先回写规范（§6），再写下层 |
| 发现矛盾，挑一个看起来合理的写下去 | 停下，修上层或登记 `P.09` |
| 用 demo 里的说法（"子系统""工具栏""气泡""挡位"） | 用 `P.06` 的标准名（子图、停靠栏、浮动回复、强度） |
| 一口气写完再记日志 | 每个子树记一次 |
| 改编号、删文档、给令牌改名 | 不允许（`G.01-R3`、`U.02-R4`） |
