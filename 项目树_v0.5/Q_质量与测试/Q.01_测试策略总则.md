# Q.01 测试策略总则

| 项 | 内容 |
|---|---|
| 编号 | Q.01 |
| 类型 | 规范 |
| 上级 | Q 质量与测试 |
| 下级 | 无 |
| 状态 | 草稿 |
| 素材 | 引12 §1、§7；`G.05.04`；`G.08` §2；`W.12` §6.1、§6.9；`P.09` K192、Q26 |
| 最后修改 | 2026-11-23 |

## 1. 目的
统一"测什么、在哪一层测、做到什么程度算够"。没有统一的分层，同一个行为会在三层里各测一遍、又有别的行为哪层都没测；没有确定性规则，CI 会出现时好时坏的测试，最后大家习惯性地点"重跑"。

## 2. 适用范围
代码仓库里的全部测试：`engine/`、`internal/`、`cmd/`、`tools/` 的 Go 测试，`web/` 的前端测试，以及写这些测试的人和实施模型。

## 3. 规则

### 3.1 分层
| 层 | 测什么 | 工具 | 在哪 | 每个合并请求都跑 |
|---|---|---|---|---|
| 单元 | 纯函数：类型兼容、环检测、Op 应用与逆操作、授权矩阵、路径 ID、预算、投影 | `go test` + testify（`G.05.04-R1`） | 各包 `*_test.go` | 是 |
| 属性 | Op 互逆、校验闭包、可交换 Op 的 rebase、三方合并、授权单调、调度安全、投影确定性（`Q.03`） | `pgregory.net/rapid` | 各包 | 是（每条性质 200 例） |
| 执行器 | 13 个执行器在 fake 模型、fake 工具下的行为 | `go test` + `llm/fake`（`Q.06`） | `engine/exec/**` | 是 |
| 调度确定性 | 整张图在虚拟时钟下运行，事件序列与黄金文件一致 | `clock.Fake` + 固定种子 | `engine/sched`、`engine/run` | 是 |
| 存储契约 | 同一套用例同时跑 memstore 与 SQLite（`E.07-R3`、`G.05.04-R7`） | `storetest.Run` | `engine/store/**` | 是 |
| API 契约 | 每个接口的请求和响应、每条 SSE 事件都按 `schema/` 校验（`B.04-R3`） | 测试中间件 + JSON Schema 校验器 | `internal/api/**` | 是 |
| 崩溃恢复 | 在事件点杀进程再续跑（`Q.09`） | 子进程 + 故障注入 | `testdata/crash/` | 抽样 10 个切点；全量每晚 |
| 前端 | 见 `W.12` §6.1 | Vitest、Playwright | `web/` | 是 |
| 性能 | 见 `W.11`、`Q.08` | — | — | 前端是；后端每晚 |
| 评测 | 不是测试（`Q` §1），见 `Q.07` | — | `evals/` | 否 |

| 编号 | 规则 |
|---|---|
| Q.01-R1 | 一个行为放在能测它的最低一层测；只有跨模块、跨进程或依赖真实浏览器的行为才放到集成和端到端层（`W.12` §6.1 是前端的同一条规则） |
| Q.01-R2 | 每个实施叶子：实施卡里的每个测试用例对应一个测试，测试名以用例编号开头（`G.05.04-R2`、`W.12` §6.8）；交付时列出编号对照（`G.14` §2 第 2 条） |

### 3.2 确定性
| 编号 | 规则 |
|---|---|
| Q.01-R3 | 合并门禁里的测试必须确定（`Q-R1`）：① 时间一律经 `clock.Clock` 取，测试用 `clock.Fake`，不用 `time.Sleep` 等待（`G.05.04-R5`）；② 随机数用固定种子，失败时打印种子（`G.05.04-R4`）；③ 不依赖执行顺序和 map 遍历顺序；④ 不访问网络（`Q.06`）；⑤ Go 测试里的时间一律用 UTC，前端按 `W.10` 在两个时区各跑一遍；⑥ 只用 `t.TempDir()` 下的文件（`G.05.04-R8`） |
| Q.01-R4 | 不稳定的测试按缺陷处理（`Q.12`）：CI 不自动重跑 Go 测试；前端端到端重试后才通过同样算失败（`W.12` §6.5）。修好之前不能用跳过来让门禁通过（`Q-R3`）；确实要临时隔离时，在合并请求里写明原因和修复期限，经人工批准 |

### 3.3 覆盖率
| 编号 | 规则 |
|---|---|
| Q.01-R5 | Go 语句覆盖率门槛以 `G.08` §2 为准：`engine/op`、`engine/schema`、`engine/sched`、`engine/authz`、`engine/run` ≥ 80%；`engine/` 下其他包 ≥ 60%；`internal/`、`cmd/`、`tools/` 不设门槛（它们靠 API 契约和端到端覆盖）。统计方式：Linux 上 `go test ./... -coverpkg=./... -coverprofile=cover.out`，按包汇总，排除 `gen/` 和 `_test.go`（`O.02` 的 `tools/ci/cover`）。引擎计划 12 号里的"90% / 75%"作废（`P.09` K192） |
| Q.01-R6 | 前端 v1 不设覆盖率门槛：统计需要新增依赖（`W.12` §6.9），前端靠实施卡的用例编号保证（Q.01-R2）。是否改为设门槛待用户确认（`P.09` Q26）；要设时按 `G.10-R2` 上报依赖，再改本条和 `W.12` §6.9 |
| Q.01-R7 | 覆盖率是下限不是目标：不为凑覆盖率写不断言任何结果的测试；评审时看新增测试有没有断言 |

### 3.4 测试数据
| 编号 | 规则 |
|---|---|
| Q.01-R8 | 只被一个包用的测试数据放该包的 `testdata/`；多个包共用的放仓库根 `testdata/`（`G.03-R5`）；示例文档和测试向量放 `schema/examples/`（`C`），测试只读不改 |
| Q.01-R9 | 输出较大的结构用黄金文件比较（`G.05.04-R3`）；更新黄金文件、截图基线（`W.12` §6.6）、性能基线（`W.11` §6.6）的提交都要单独说明原因 |
| Q.01-R10 | 测试数据里不出现真实的密钥、个人信息和用户内容；录放数据按 `Q.06-R5` 脱敏 |

### 3.5 每个合并请求与每晚
| 编号 | 规则 |
|---|---|
| Q.01-R11 | 每个合并请求跑 §3.1 表里"是"的全部；每晚跑崩溃恢复全量、后端性能、漏洞扫描、可复现构建（`O.02` §6.3）。每晚失败不阻断合并，但要在 2 个工作日内作为缺陷处理 |

## 4. 检查方式
- 自动：`O.02` 的 `go-test`（含 `tools/ci/cover`）、`web`、`e2e` 任务；`W.12` 的 `test:ids` 列出用例编号。
- 评审：交付说明里的用例编号对照是否完整（Q.01-R2）；新增测试有没有真正的断言（R7）；有没有 `time.Sleep`、未固定的随机数、`t.Skip`（R3、R4）。

## 5. 例外
- 依赖操作系统能力的测试（例如密钥库、文件权限）可以只在对应平台运行，用构建标签或 `runtime.GOOS` 判断，并在测试名里写明平台。
- 除此之外无例外。
