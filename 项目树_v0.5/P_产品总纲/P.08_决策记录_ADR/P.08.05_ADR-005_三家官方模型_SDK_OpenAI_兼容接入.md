## 背景
首批要支持 OpenAI 兼容、Anthropic、Gemini 三类模型；国内厂商和本地模型大多提供 OpenAI 兼容接口。

## 考虑过的方案
| 方案 | 优点 | 缺点 |
|---|---|---|
| 自己直连各家 REST | 零依赖 | 各家流式、工具调用、结构化输出细节多，维护成本高 |
| 统一的第三方聚合库 | 一套接口 | 跟进新特性慢；出问题难排查 |
| 三家官方 Go SDK + 统一适配层 | 跟进最快、行为最准确 | 要写适配层 |

## 决定
使用 `openai-go`、`anthropic-sdk-go`、`google.golang.org/genai` 三个官方 SDK，在 `engine/llm` 上做统一接口；各家差异写进 quirks 表（INV-18）。国内厂商和本地模型通过 OpenAI 兼容 + `base_url` 接入。

## 理由
官方 SDK 对流式、工具调用、结构化输出支持最完整；差异写成数据便于新增厂商。

## 代价与后果
- 每家能力差异必须在 M0 做验证并写进 quirks 表（例如某些模型的推理强度只支持 low / high / max，不支持 medium）。

## 推翻条件
某家官方 SDK 停止维护，或出现必须接入、但没有 OpenAI 兼容接口的重要厂商。
