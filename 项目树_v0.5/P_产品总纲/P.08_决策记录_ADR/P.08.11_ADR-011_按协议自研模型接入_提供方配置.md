## 背景
ADR-005 按厂商选型：用 OpenAI、Anthropic、Google 三家的官方 Go SDK，各写一个适配器。第 ⑨ 片复查时用户指出，这和本项目"可扩展、高度自定义"的宗旨不合：
- 市面上的厂商、中转站、私有部署、本地模型，绝大多数讲的是少数几种接口协议（Chat Completions、Responses、Anthropic Messages）；按厂商写适配器，接一家就要改一次代码。
- NewAPI 这类网关的做法是"渠道"：协议是固定的几种，地址、鉴权、请求头、模型名映射、参数改写都写在配置里。用户希望照这个思路做。
- ADR-005 没有 Responses 协议；三家 SDK 都是频繁升级的外部依赖。
- 以后的自定义节点（ComfyUI 这类不是对话的 API）要能复用同一套连接、密钥和出站规则。

## 考虑过的方案
| 方案 | 优点 | 缺点 |
|---|---|---|
| 三家官方 SDK + 适配层（ADR-005） | 跟进新特性快 | 按厂商而不是按协议；接新厂商要改代码；三个外部依赖跟着升级；没有 Responses |
| 第三方聚合库 | 一套接口 | 跟进慢、出问题难排查；又多一个依赖 |
| **按协议自研 + 提供方配置** | 新增厂商只改配置；中转站、本地模型、私有部署都能接；没有外部依赖；行为完全可控 | 自己维护三种协议的编码和解码 |

## 决定
1. `engine/llm` 只实现主流接口协议，M0 三种：`chat_completions`、`responses`、`anthropic_messages`；全部用 Go 标准库自己实现（`E.10-R6`），不引入任何厂商 SDK 和聚合库。Gemini 先走它的 Chat Completions 兼容接口，原生协议需要时再加一个协议包（`E.10-R7`）。
2. 每个**模型提供方**（相当于 NewAPI 的渠道）是一份配置：协议、地址、路径、鉴权方式、额外请求头、模型列表与上游名映射、请求体覆盖（设置 / 删除 / 改名字段）、能力覆盖、超时、代理（`E.10.01` §4.3）。在界面上是一种连接（`C.16`）。
3. 厂商差异只写在数据里：quirks 表（能力、错误规则）、常用厂商、提供方的请求体覆盖（INV-18，`E.10.05`）。协议代码里不出现厂商名（`quirkscheck`）。
4. 多密钥轮询、优先级、故障转移：M0 配置格式先留好字段，M1 实现（`P.09` K250）。
5. 不是对话的 API（ComfyUI、出图、语音……）不接进模型提供方，按工具和声明式 http 节点接入，和模型提供方共用连接、密钥库、出站规则；多步、异步、文件结果的写法在 M2 做（`E.10` §3）。

## 理由
- 和项目宗旨一致：能力由配置和数据扩展，不由代码分支扩展（INV-18、`X.01`）。
- 协议的数量远少于厂商的数量，而且协议本身比各家 SDK 稳定。
- 符合 ADR-010（只参考、不引入）：不需要额外的第三方代码。

## 代价与后果
- 三种协议的编码、流式解码、错误格式由本项目维护；协议出新字段时要跟进。靠共用的契约测试和录放（`E.10-R3`、`Q.06`）保证行为不倒退。
- 没有 SDK 的类型保护，请求体是我们自己拼的；必须对照官方文档和真实录制（M0 用 Mistral 录 Chat Completions 和 Responses）。
- 某家的私有特性（例如 Vertex 的鉴权方式）要等用到时再加协议或鉴权方式。
- `G.10` 去掉三个 SDK；ADR-005 改为"已取代"。

## 推翻条件
- 出现必须接入的重要厂商，只提供私有协议，且差异无法用配置（路径、鉴权、请求头、请求体覆盖）表达，同时又不值得为它单独写一个协议包。
- 协议变化快到维护成本明显高于引入官方 SDK。
