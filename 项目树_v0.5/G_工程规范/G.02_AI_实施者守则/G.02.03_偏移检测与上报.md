## 1. 目的
模型遇到矛盾时最容易犯的错，是"选一个看起来合理的继续做"。这样问题被藏进了代码里，后面越积越多。本规则要求**停下来、写清楚、交给设计方决定**。

## 2. 必须上报的情况
| 编号 | 情况 | 例子 |
|---|---|---|
| G.02.03-R1 | 文档之间矛盾 | 叶子说返回 404，`C.11` 错误码表里没有这个码 |
| G.02.03-R2 | 文档和现有代码矛盾 | 叶子要求调用 `store.Runs().Get`，但已实现的接口叫 `Find` |
| G.02.03-R3 | 文档没写，又必须决定，且决定会影响接口、不变量或其他模块 | 没写并发冲突时该返回什么 |
| G.02.03-R4 | 需要改白名单以外的文件 | 需要给 `engine/graph` 加一个辅助函数 |
| G.02.03-R5 | 需要新依赖 | 想用某个第三方库 |
| G.02.03-R6 | 需要改契约 | 想给事件加一个字段 |
| G.02.03-R7 | 按文档实现会违反某条不变量 | 文档的写法会导致绕过 Op 直接写库 |
| G.02.03-R8 | 验收用例本身有错 | 期望输出和规则对不上 |

## 3. 上报后怎么做
- **G.02.03-R9** 写上报单后，**停止受影响部分的实施**。和问题无关的部分可以继续。
- **G.02.03-R10** 不允许"先按自己的理解做，上报单里说明"。必须等裁决。
- **G.02.03-R11** 一个问题一份上报单。

## 4. 上报单格式
文件放在 `sj/反馈/`，文件名 `{日期}_{叶子编号}_{简述}.md`：
```markdown
# 上报 · {叶子编号} · {一句话问题}

| 项 | 内容 |
|---|---|
| 类型 | R1 文档矛盾 / R2 代码矛盾 / R3 未定义 / R4 越界 / R5 新依赖 / R6 改契约 / R7 违反不变量 / R8 用例错误 |
| 发现于 | 任务包 {叶子编号}，{日期} |
| 涉及文档 | 编号 + 小节 |
| 涉及代码 | 文件路径 + 行号 |
| 阻塞程度 | 全部阻塞 / 部分阻塞（写明哪部分还能继续） |

## 现象
（原文引用两处矛盾的内容）

## 可选方案
| 方案 | 影响 |
|---|---|
| A | … |
| B | … |

## 建议
（选哪个，为什么。只是建议，不代表已经实施）
```

## 5. 设计方的处理
1. 裁决写进对应文档（改文档，而不是只回复上报单）。
2. 在上报单末尾写"已裁决：见 {编号} {小节}"。
3. 如果是待决问题，追加到 `P.09`。
