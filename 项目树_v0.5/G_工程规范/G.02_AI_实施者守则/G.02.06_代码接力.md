## 1. 目的
代码由多个模型（和人）轮流接手完成。`G.02` 到 `G.02.05` 管"一个任务怎么做"，本文管**任务和任务之间怎么交接**：新来的从哪看、怎么领活、做到一半断了怎么接、怎么防止一棒一棒越做越偏、谁来证明做对了。

不管这些会出现的问题：新模型不知道从哪读起，挑着读，读漏了就自作主张；进度靠手写，很快和实际对不上；上一棒留下一堆没提交的改动，下一棒分不清哪些可信；每一棒都"有道理"地改一点，累积起来偏离设计；文档改了，按旧文档写好的代码没人知道要复查；写代码的模型自己说"测过了"。

## 2. 适用范围
代码仓库（`mio-cc/Anywhere-Door`，`O-R7`）里的全部实施工作，以及参与的每一个模型和人。设计方（拍板的人和替他整理文档的模型）同样遵守。

## 3. 规则

### 3.1 两个仓库、一个入口
| 编号 | 规则 |
|---|---|
| G.02.06-R1 | 设计文档留在设计仓库（`sj/项目树_v0.5`，推送到 `mio-cc/miocode`），不复制进代码仓库（`G.03` §2）。代码仓库找设计文档的位置：环境变量 `ANYDOOR_DOCS`；没设时为 `../sj/项目树_v0.5`（两个仓库放在同一个父目录下） |
| G.02.06-R2 | 代码仓库的入口只有一个：根目录的 `AGENTS.md`。它只写四件事：这是什么、开工步骤、硬规则摘要、常用命令；其余一律指向设计文档。`CLAUDE.md` 等其他工具约定的入口文件只有一行"见 AGENTS.md"。`AGENTS.md` 和设计文档冲突时以设计文档为准，并当作缺陷修 `AGENTS.md` |
| G.02.06-R3 | 每一棒开工按 `AGENTS.md` 的开工步骤：读 `AGENTS.md` → `go run ./tools/relay status` → 读 `RELAY.md` 最上面一条 → 续做或领取。没有执行这几步就动手的改动，评审时直接退回 |

### 3.2 领取：一次一个叶子
| 编号 | 规则 |
|---|---|
| G.02.06-R4 | 只能领取状态为"已审"的实施叶子（`G.02.01-R2`）；一棒同一时间只领一个。领取用 `go run ./tools/relay start <叶子>`：检查状态、检查没有别人领着、建分支 `feat/<叶子>-<简称>`（`G.07-R2`）、在 `RELAY.md` 写领取记录、生成任务包 |
| G.02.06-R5 | 任务包由 `relay start` 按 `G.02.01` §3、`G.02.02` 自动拼出，放在 `.relay/tasks/<叶子>.md`（不提交）。实施者**只读任务包**，不自己去树里挑文档；任务包缺了必须读的东西，说明文档漏了引用，按 `G.02.03` 上报，不要自己补读 |
| G.02.06-R6 | 领取时把"依据"记下来并提交：`docs/relay/<叶子>.json` 记录设计仓库的提交号和任务包里每份文档的 SHA-256（`G.02.01` §3 F 节）。代码只对这一版文档负责 |
| G.02.06-R7 | 多棒并行只在两个任务的文件白名单不重叠时允许；`relay start` 检查重叠。公共文件（`web/eslint.config.js`、`components/ui/index.ts` 这类）只能在标明的区段追加。M0 阶段一律串行 |

### 3.3 做的过程中：随时可能断
| 编号 | 规则 |
|---|---|
| G.02.06-R8 | 按实施卡分步：每完成一条（或一个测试用例）就提交一次，提交信息按 `G.07-R3`，正文最后一行 `Refs: <叶子>`；不攒一大批最后一起提交 |
| G.02.06-R9 | 每提交一次（至少每 30 分钟），更新 `RELAY.md` 本棒记录的"进行中"：停在实施卡第几条、下一步做什么、有没有没想清楚的地方 |
| G.02.06-R10 | 一个叶子的验收需要另一个还没实现的叶子时，可以写**桩**：放在那个叶子将来的位置，只实现本叶子用到的最少部分，每个桩文件第一行写 `// STUB(<那个叶子的编号>): <为什么需要>`。桩要登记在本棒记录里；`relay status` 列出全部桩；那个叶子实施时整体替换桩，不在桩上改 |
| G.02.06-R11 | 发现文档矛盾或文档不够写，按 `G.02.03` 写上报单并停下受影响的部分（`G.02-R4`）；在 `RELAY.md` 写明"阻塞：上报单 <文件名>" |

### 3.4 接手：不信口头，只信检查
| 编号 | 规则 |
|---|---|
| G.02.06-R12 | 接手一个做到一半的叶子：先 `go run ./tools/relay check <叶子>`，以检查结果为准，不以上一棒在 `RELAY.md` 里写的"已完成"为准。工作区里有上一棒没提交的改动时：检查通过就作为一次提交接下来（提交信息写"接上一棒未提交的改动"）；不通过就先 `git stash`，记进本棒记录，从最后一次提交接着做 |
| G.02.06-R13 | 接手前 `relay check` 会比较依据（R6）和当前设计文档：任务包里有文档在领取之后改过，先读改动（`relay diff <叶子>` 列出变化的文档和小节），确认代码要不要跟着改，记进本棒记录，再继续 |

### 3.5 防止跑偏：能机器查的都机器查
| 编号 | 规则 |
|---|---|
| G.02.06-R14 | `go run ./tools/relay check <叶子>` 是交付前和接手时必须跑的检查，内容（任何一项不通过即失败）：① 改动的文件都在任务包的白名单里（`G.02-R3`）；② 没有改 `schema/`、`gen/`、`*/generated/`（`G.02.05-R1`、`R4`），除非白名单明确允许；③ `go.mod`、`web/package.json` 没有新增直接依赖，或新增的都在 `tools/deps/allow.txt` 里（`G.10`）；④ 没有删除或跳过已有测试：比较分支起点，找被删除的测试函数、新增的 `t.Skip`、`.skip(`、`.only(`；⑤ 实施卡里每个测试用例编号都出现在测试名开头（`Q-R4`）；⑥ 依据文档没有变（R13）；⑦ `go run ./tools/build -check`（`O.01`）通过 |
| G.02.06-R15 | `relay check` 只能证明"没越界、没漏测、能编译能测"，证明不了"做的是对的"。所以交付还要过**交叉评审**（R17）。两者都通过才算交付 |
| G.02.06-R16 | 实施者不能修改 `tools/relay/`、`tools/ci/`、`tools/build/` 来让自己的检查通过；这几个目录只在实施它们自己的叶子（`O.01`、`O.02`）时改 |

### 3.6 验证：由另一方执行
| 编号 | 规则 |
|---|---|
| G.02.06-R17 | 三个角色：**实施者**写代码；**验证者**在开发机上执行 `relay check` 和任务包"必须通过的命令"，原样贴出输出，不改代码；**评审者**拿任务包和本次改动，对照实施卡逐条看，专找"检查都过了但意思不对"的地方，写评审记录。同一个叶子的评审者不能是它的实施者（换一个模型，或由人评审）；验证者可以和评审者是同一个。各方说法不一致时，以命令的原始输出为准 |
| G.02.06-R18 | 评审记录追加在 `docs/relay/<叶子>.review.md`：一张表，列为 `# · 实施卡 / 小节 · 结论 · 说明`；"结论"一格只写"符合 / 不符合 / 有疑问"中的一个词，不符合或有疑问时在"说明"里写依据（文档编号和小节、代码文件和行号）。有"不符合"时退回实施者；"有疑问"由设计方裁决。实施者在表下面的"实施者处理"一节逐条写怎么处理的；**由评审者**复核后，在那一行的"说明"末尾加"已处理（复核：评审者，日期）"——`relay status` 只把结论为"不符合 / 有疑问"且没有"已处理"的行算作没处理完（`P.09` K199） |
| G.02.06-R19 | 核心包（`engine/op`、`engine/authz`、`engine/sched`、`engine/run`）可以由设计方指定"测试先行"：一方只按实施卡写测试并先合并，另一方只写实现，不能改那批测试。是否指定，写在任务包里 |

### 3.7 交接与冻结
| 编号 | 规则 |
|---|---|
| G.02.06-R20 | 收工（或感觉上下文快用完）时：提交全部改动；`relay check` 的结果贴进本棒记录；在 `RELAY.md` 最上面写完本棒记录（模板在 `RELAY.md` 顶部）：完成了什么、进行中停在哪、下一步、桩、上报单、检查结果、推送情况 |
| G.02.06-R21 | 叶子合并进 `main` 后，设计方把设计仓库里该叶子的状态从"已审"改为"冻结"，"最后修改"写合并日期，在"变更记录"加一行写代码仓库的合并提交号（文件头的日期格式固定为 YYYY-MM-DD，`check_tree` E3；`G.14` §3）。冻结之后要改这个叶子的文档，先改回"已审"并说明原因；`go run ./tools/relay stale` 列出"依据文档在冻结后又被改过"的叶子，它们的代码需要复查 |
| G.02.06-R22 | 进度只从事实推出来，不手写：叶子状态看设计文档的文件头；代码完成到哪看 `relay status`（领取记录、分支、测试用例编号的覆盖、桩）；`RELAY.md` 只写"人才知道的事"（停在哪、为什么、下一步） |

## 4. 检查方式
| 规则 | 怎么查 |
|---|---|
| R3、R12、R13、R14、R22 | `go run ./tools/relay status` / `check` / `diff` / `stale`（`O.01` §4.5） |
| R4–R7 | `relay start` 拒绝不合规的领取 |
| R8 | `O.02` 的 `commitcheck` |
| R14 ⑦、R16 | `O.02` 的 CI 再跑一遍；改了 `tools/relay/` 等目录而分支不是对应叶子时 `allowlist` 失败 |
| R17、R18 | 合并请求必须附验证输出和评审记录，`G.08-R3` 的人工批准时核对 |
| 其余 | 评审时看 `RELAY.md` 的本棒记录 |

## 5. 例外
- **第 0 片（初始化）与第 1 片（`O.01`，含 `tools/relay` 本身）**：`tools/relay` 还没写好，R3、R4、R6、R12–R14 改为人工执行：设计方在 `RELAY.md` 手工写领取记录和依据（设计仓库的提交号），验证者手工跑 `relay check` 对应的各项（`git diff --name-only` 对白名单、`go run ./tools/build -check`）。`tools/relay` 合并之后，从下一个叶子起照常执行。
- 除此之外无例外。
