## 1. 目的
后续的代码由 AI 模型实施。模型最常见的问题不是写不出代码，而是**自作主张**：顺手改了接口、引入了没登记的库、文档没写的地方自己发明一套、为了让测试通过而改测试。每一次自作主张单独看都"有道理"，累积起来就让系统偏离设计。

本守则是给实施模型的硬规则。**派给模型的每个任务，都必须把本文和 `G.02.05` 禁止事项总表放进上下文。**

## 2. 适用范围
所有由 AI 模型执行的实施任务：写代码、写测试、改配置、改文档。人工实施者同样适用。

## 3. 五条总原则
| 编号 | 原则 | 说明 |
|---|---|---|
| G.02-R1 | **文档是唯一依据** | 只实现叶子文档和实施卡写明的内容。文档没写的行为，不实现；文档写了的，不省略 |
| G.02-R2 | **契约不可改** | `C` 契约层、`schema/` 文件、生成的代码、事件名、错误码、Op 类型，实施时一律不改。需要改时上报 |
| G.02-R3 | **边界不越过** | 只改实施卡"要建 / 要改的文件"里列出的文件。需要动其他文件时上报 |
| G.02-R4 | **矛盾就停** | 发现文档之间矛盾、文档和现有代码矛盾、文档不够写不下去时，停止实施，按 `G.02.03` 写上报单，不自己选一个 |
| G.02-R5 | **验证再交** | 交付前跑完 `G.02.04` 自检清单。测试不通过时修代码，不改测试、不跳过测试 |

## 4. 允许模型自主决定的范围
不是所有细节都要上报。以下情况模型可以自己决定，但要在交付说明里写明：
- 私有函数、私有变量的命名和拆分（遵守 `G.04`）。
- 实施卡没规定的内部实现细节（例如用切片还是 map），前提是不影响接口、不影响不变量、不引入新依赖。
- 额外的单元测试（只能多，不能少）。
- 代码注释。

## 5. 派任务与交付
| 环节 | 规则 | 详见 |
|---|---|---|
| 派任务时附带什么 | 任务包格式 | `G.02.01` |
| 模型该读哪些文档 | 上下文最小集 | `G.02.02` |
| 发现问题怎么办 | 上报单 | `G.02.03` |
| 交付前检查什么 | 自检清单 | `G.02.04` |
| 绝对不能做什么 | 禁止事项总表 | `G.02.05` |

## 6. 交付说明格式
每次交付必须附一份交付说明：
```markdown
## 交付说明 · {叶子编号} {名称}
- 改动的文件：（逐个列出，标明新建 / 修改）
- 实现了实施卡的哪些条目：（逐条对应）
- 自主决定的细节：（第 4 节范围内的决定）
- 测试：新增 N 个；全部通过的命令和输出摘要
- 自检清单：G.02.04 全部勾选 / 未勾选项及原因
- 上报单：无 / 编号列表
```

## 7. 检查方式
- 评审时逐条对照交付说明和实施卡。
- CI 检查：只改了允许的文件（对比任务包里的文件白名单）；生成物一致；依赖清单未变或已登记。
