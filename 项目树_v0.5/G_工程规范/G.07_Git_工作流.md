## 1. 目的
统一分支、提交和合并方式，让历史可读、可追溯到文档树节点。

## 2. 规则
| 编号 | 规则 |
|---|---|
| G.07-R1 | 主干开发：只有一个长期分支 `main`，任何时候都能构建、测试通过 |
| G.07-R2 | 每个实施任务（一个叶子）一个短分支：`feat/E.14.07-aggregate`、`fix/W.06.13-peek-position`；分支名带叶子编号 |
| G.07-R3 | 提交信息用 Conventional Commits：`<类型>(<范围>): <描述>`；类型只用 `feat fix refactor perf test docs build ci chore`；范围写叶子编号；描述用中文，一句话 |
| G.07-R4 | 提交正文写"为什么"，并在最后一行写 `Refs: <叶子编号>`；关联上报单时写 `Refs: 反馈/<文件名>` |
| G.07-R5 | 破坏性修改在正文写 `BREAKING CHANGE: …`，并且必须有对应的 ADR（`P.08`） |
| G.07-R6 | 合并方式：squash merge，合并后的提交信息就是 PR 标题（同样遵守 R3） |
| G.07-R7 | 不提交：密钥、`.env`、`web/dist/`、`node_modules/`、个人 IDE 配置、大于 1MB 的二进制文件（字体、图标例外，需登记在 `G.17`） |
| G.07-R8 | 发布用标签 `v主.次.修订`，只能从 `main` 打 |

## 3. 例子
```
feat(E.14.07): 实现聚合执行器的 group_ratio、vote、dedupe 算子

聚合必须是确定性的（kernel 锁 deterministic=true），所以算子实现里不使用 map 遍历顺序，
先按 key 排序再分组。

Refs: E.14.07
```

## 4. PR 模板（`.github/pull_request_template.md`）
```markdown
## 叶子编号
## 改了什么（对应实施卡条目）
## 自主决定的细节（G.02 §4）
## 测试
## 自检清单（G.02.04）
- [ ] A 范围  - [ ] B 契约与不变量  - [ ] C 依赖  - [ ] D 质量  - [ ] E 规范
## 文件白名单（实施任务必填：从任务包 B 节原样复制，CI 据此检查，`O.02` §4.3）
## 截图（界面改动必填）
```

## 5. 检查方式
`go run ./tools/ci/commitcheck`（CI 检查 PR 标题和提交信息，`O.02` §4.3；原定的 `commitlint` 是 npm 包、不在 `G.10` 清单里，`P.09` K189）；`gitleaks`（密钥扫描，`S.12`）。
